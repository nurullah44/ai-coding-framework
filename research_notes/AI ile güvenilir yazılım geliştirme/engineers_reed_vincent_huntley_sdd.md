# Spec-first workflows for AI coding agents: Harper Reed, Jesse Vincent (Superpowers), Geoffrey Huntley (Ralph), and spec-driven development as reviewed by Birgitta Böckeler (Kiro, Spec Kit, Tessl)

Research date: 2026-10-14. "First-hand" = written by the person or the tool's own repo/docs. "Secondary" = someone else's summary. Repo files were read at `main` on 2026-10-14 via raw.githubusercontent.com / `gh api` (no code was run).

## Harper Reed: the "LLM codegen workflow" (idea → spec → plan → execution), prompts, spec checks, later updates

### Takeaway
Harper Reed's workflow (Feb 2025) is three "discrete loops": a chat model asks one question at a time to build `spec.md`; a reasoning model turns the spec into `prompt_plan.md` (a series of small, test-driven codegen prompts) plus a `todo.md` checklist; a coding tool executes one prompt at a time. "Done" per step is "tests pass, the program builds/runs", commit, mark the prompt complete, pause for human review. His spec is not formally checked — the human reads it, and tests, linting and pre-commit hooks are the guardrails. His public writing after May 2025 moved away from this workflow topic; the only later trace found is a Sept 2026 bug report he gave to Superpowers.

### Cited Findings
**Original workflow — "My LLM codegen workflow atm" (2025-02-16, first-hand)** — [harper.blog](https://harper.blog/2025/02/16/my-llm-codegen-workflow-atm/)
- Summary line: "Brainstorm spec, then plan a plan, then execute using LLM codegen. Discrete loops." He credits friends incl. "Obra" (Jesse Vincent) and warns: "This is working well NOW, it will probably not work in 2 weeks, or it will work twice as well."
- Step 1 idea-honing prompt (verbatim): "Ask me one question at a time so we can develop a thorough, step-by-step spec for this idea. Each question should build on my previous answers, and our end goal is to have a detailed specification I can hand off to a developer. Let's do this iteratively and dig into every relevant detail. Remember, only one question at a time."
- Spec compile prompt (verbatim): "Now that we've wrapped up the brainstorming process, can you compile our findings into a comprehensive, developer-ready specification? Include all relevant requirements, architecture choices, data handling details, error handling strategies, and a testing plan so a developer can immediately begin implementation." Saved as `spec.md`.
- Spec "checking" is informal: he has used the spec to ask "a reasoning model to poke holes in the idea (must go deeper!)".
- Step 2 planning prompt (TDD version, verbatim excerpt): "Draft a detailed, step-by-step blueprint for building this project. Then, once you have a solid plan, break it down into small, iterative chunks that build on each other. Look at these chunks and then go another round to break it into small steps. Review the results and make sure that the steps are small enough to be implemented safely with strong testing, but big enough to move the project forward. ... provide a series of prompts for a code-generation LLM that will implement each step in a test-driven manner. ... There should be no hanging or orphaned code that isn't integrated into a previous step." Output saved as `prompt_plan.md`; then "Can you make a `todo.md` that I can use as a checklist? Be thorough." — `todo.md` is "good for keeping state across sessions."
- "This entire process will take maybe 15 minutes." Execution "success really depends on how well step 2 went." Per-step check: "run code, run tests, etc ... if it works, move on to next prompt; if it doesn't work, use repomix to pass the codebase to claude to debug".
- Brownfield ("Non-greenfield"): "The planning is done per task, not for the entire project." Uses repomix + `llm` prompt templates to generate code review, GitHub issues and missing-test lists; prompts such as "You are a senior developer. Your job is to review this code, and write out the top issues ... Do Not Hallucinate."
- Failure mode he names: "you have to aggressively keep track of what's going on because you can easily get ahead of yourself" ("over my skis"); "a planning step ... can help keep things under control. At least you will have a doc you can double-check against."
- Limit he names: "it is largely a solo endeavor ... These workflows are not easy to use as a team. The bots collide, the merges are horrific".

**Update — "Basic Claude Code" (2025-05-08, first-hand)** — [harper.blog](https://harper.blog/2025/05/08/basic-claude-code/)
- Same flow, now Claude Code: "I chat with gpt-4o to hone my idea; I use the best reasoning model I can find to generate the spec ... I use the reasoning model to generate the prompts ... I save the spec.md, and the prompt_plan.md in the root of the project."
- Execution prompt (verbatim): "1. Open @prompt_plan.md and identify any prompts not marked as completed. 2. For each incomplete prompt: - Double-check if it's truly unfinished (if uncertain, ask for clarification). - If you confirm it's already done, skip it. - Otherwise, implement it as described. - Make sure the tests pass, and the program builds/runs - Commit the changes to your repository with a clear commit message. - Update @prompt_plan.md to mark this prompt as completed. 3. After you finish each prompt, pause and wait for user review or feedback. 4. Repeat with the next unfinished prompt as directed by the user."
- On TDD: "Most of the testing was added AFTER the core work was done. This is fine for humans. THIS IS BAD FOR ROBOTS. The robots LOVE TDD." — "It is the most effective counter to hallucination and LLM scope drift I have found."
- Pre-commit hooks as the gate: "The robot REALLLLLY wants to commit. So when you instruct it to do some code and then commit ... it will make wild code changes, commit the code, inevitably fuck it all up and then have to fix it." Hooks run "tests, type checking, linting".
- Uses Jesse Vincent's CLAUDE.md ("instructions on how to do TDD"). "Most of the time the plans are about 8–12 steps. I can usually get through a Greenfield development plan in about 30–45 minutes regardless of apparent complexity or language." Example: a BASIC interpreter in C, "The first version worked within an hour ... Would it ship it in 1982? Probably not." (anecdote, self-reported)

### Inferences
- Reed's "done" is per prompt and mostly mechanical (tests pass + builds/runs + commit + checkbox), with the human as reviewer after each prompt. There is no separate reviewer agent and no acceptance criteria per step beyond what the generated prompt says.
- His spec prompt asks for "architecture choices, data handling details, error handling strategies, and a testing plan", so architecture is in the spec only as one heading the LLM fills in; no explicit security or network layer.
- His prompt-plan "prompts" are themselves the tickets; the todo.md checklist is the state.

## Jesse Vincent / Superpowers: skills, plans a weaker agent can follow, how "done" is enforced

### Takeaway
Superpowers (current release v7.0.0, 2026-10-10) is a set of mandatory skills that chain brainstorming → written design (spec) → plan → subagent-driven or inline execution → review → finish, with "done" enforced by gates: fresh test evidence, a per-task reviewer that gives separate spec-compliance and quality verdicts, an inline-execution ledger line written by a passing test command (subagent execution records its own review completion), and a final whole-branch review. Its plan format has moved from "complete code for a zero-context engineer" (2025) to "record the decisions, not the code" (Sept 2026), and Jesse reports Haiku can often do implementation from such plans — but his own eval notes show where cheap models and reviewers fail.

**Current skill texts (first-hand, main @ 2026-10-14)**
- Brainstorming: "You build what you believe your human partner wants, and that belief is usually thinner than it feels." Sizes work: quick task → do it; small change → agreed in chat; project → "a written design document" then a full plan. Design doc covers "intent and the why; goals, non-goals, anti-goals; constraints; the parts of the how they decided, as they decided them; what's left to the builder". HARD-GATE: "Nothing gets built until your human partner approves the full description". Plays back understanding "in about 200-300 words" and marks guesses as guesses — [brainstorming/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)
- Spec check = "builder check": a fresh subagent prompt: "You've been handed a design document and asked to put together a plan to build what it describes. You will not be able to talk to the person who wrote it. ... Report only the questions you'd still need answered ... places where you'd have to guess and a wrong guess would matter." — [brainstorming/builder-check-prompt.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/builder-check-prompt.md)
- Writing plans: "What they cannot know is what you decided: which files, which names and signatures, which values from the spec, which tests prove each task. Document those." Header requires Goal, Architecture ("2-3 sentences about approach"), Tech Stack, Spec path, **Global Constraints** ("exact values copied verbatim from the spec"), **Review Focus** (five untested input classes/failure modes). Each task lists Files (Create/Modify with line ranges/Test), **Interfaces** (Consumes/Produces exact signatures), checkbox steps: failing test → run, "Expected: FAIL with ..." → implement signature → run, "Expected: PASS" → commit — [writing-plans/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)
- Step rule: "A step is done when the implementer can write exactly one reasonable thing from it. That is the whole requirement: unambiguous, not complete." "A verification step: the command to run and the output that means it passed." "A plan longer than the code it describes has written the code instead. Lines that decide nothing ('TBD', 'handle edge cases', 'add appropriate validation', 'write tests for the above', a type or function no task defines) are the opposite failure" — [writing-plans/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)
- Task sizing: "A task is the smallest unit that carries its own test cycle and is worth a fresh reviewer's gate ... split only where a reviewer could meaningfully reject one task while approving its neighbor." Plan self-review: spec coverage, step scan, type consistency ("A function called `clearLayers()` in Task 3 but `clearFullLayers()` in Task 7 is a bug."), Review Focus, proportion — [writing-plans/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)
- Model selection for executing agents: "Mechanical implementation tasks (isolated functions, clear specs, 1-2 files): use a fast, cheap model"; "the cheapest models routinely take 2-3× the turns on multi-step work — costing more overall. Use a mid-tier model as the floor for reviewers and for implementers working from prose descriptions. When the task's plan text contains the complete code to write, the implementation is transcription plus testing: use the cheapest tier"; final whole-branch review "on the most capable available model" — [subagent-driven-development/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)
- SDD loop: per task a `task-brief` file (exact values appear "only in the brief"; "Never make a subagent read the whole plan file"), implementer returns DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT with TDD RED/GREEN evidence in a report file; a reviewer gets brief + report + diff package and must return both a spec verdict and a quality verdict; fix loop max 5 rounds (rounds 4-5: fresh implementer "on a more capable model"); then "the breaker" — controller adjudicates and records `Ruling:` lines; final review on most capable model; "Never move to the next task while the review has open Critical/Important issues that are neither fixed nor parked-with-ruling at the cap." — [subagent-driven-development/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md), [implementer-prompt.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/implementer-prompt.md)
- Implementer escalation: "It is always OK to stop and say 'this is too hard for me.' Bad work is worse than no work." STOP when "The task requires architectural decisions with multiple valid approaches" — [implementer-prompt.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/implementer-prompt.md)
- Reviewer: "Treat the implementer's report as unverified claims about the code"; checks Missing / Extra / Misunderstood; "If a requirement cannot be verified from this diff alone ... report it as a ⚠️ item"; a plan-mandated defect is still "Important, labeled plan-mandated. The plan's authorship does not grade its own work" — [task-reviewer-prompt.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/task-reviewer-prompt.md)
- Final reviewer: "The spec is a vision document ... a reasonable person's expectation is a requirement, and a spec's silence is not permission"; must list a "Declined to judge" section; verdict "Ready to merge? [Yes | No | With fixes]" — [requesting-code-review/code-reviewer.md](https://github.com/obra/superpowers/blob/main/skills/requesting-code-review/code-reviewer.md)
- Inline "done" contract: "Every test the brief names exists and ran in this task ... Every `Expected:` line in the brief was compared against real output. ## Geoffrey Huntley: the Ralph loop, specs folder and fix_plan, claims, failure modes

### Takeaway
Ralph is "a Bash loop" that feeds the same prompt to a coding agent again and again; each loop loads the same specs (`specs/*`, one file per topic, written after a long requirements conversation) and a prioritized `fix_plan.md`, does "one item per loop", runs the tests for that unit, updates the plan, commits. Huntley's "done" is whatever the back pressure (types, compiler, tests, static analysis, later pre-commit hooks and deterministic simulation) accepts — not a written acceptance criterion. He claims big results (a new programming language, a "$50k" contract for "$297"), names concrete failure modes (placeholder implementations, duplicate implementations after a wrong search, broken builds overnight, wrong specs), and by Oct 2026 tells people to "delete your skill packs" and put the whole system under test instead.

### Cited Findings
**The original technique — "Ralph Wiggum as a 'software engineer'" (published 2025-07-14, updated 2026-02-19, first-hand)** — [ghuntley.com/ralph](https://ghuntley.com/ralph/)
- "Ralph is a technique. In its purest form, Ralph is a Bash loop. `while :; do cat PROMPT.md | claude-code ; done`" and "the technique is deterministically bad in an undeterministic world."
- Specs: "Specs are formed through a conversation with the agent at the beginning phase of a project. Instead of asking the agent to implement the project, what you want to do is have a long conversation with the LLM about your requirements ... it's at that point that you issue a prompt to write the specifications out, one per file, in the specifications folder."
- Each loop "deterministically allocate[s] the stack the same way": "The items that you want to allocate to the stack every loop are your plan ('@fix_plan.md') and your specifications."
- "you need to ask Ralph to do one thing per loop. Only one thing ... you also need to trust Ralph to decide what's the most important thing to implement." Reason: "you only have approximately 170k of context window ... The more you use the context window, the worse the outcomes you'll get." Main context "should operate as a scheduler", spawning subagents; "only a single subagent should be used for validation" (build/test) to avoid "bad form back pressure".
- Planning prompt (verbatim excerpt): "First task is to study @fix_plan.md (it may be incorrect) and is to use up to 500 subagents to study existing source code in src/ and compare it against the compiler specifications. From that create/update a @fix_plan.md which is a bullet point list sorted in priority of the items which have yet to be implemeneted. ... Consider searching for TODO, minimal implementations and placeholders." Asked "how do you plan?": "I don't. The models know what a compiler is better than I do. I just ask it."
- Build prompt "done" lines (verbatim): "After implementing functionality or resolving problems, run the tests for that unit of code that was improved." / "When the tests pass update the @fix_plan.md`, then add changed code and @fix_plan.md with 'git add -A' ... 'git commit' ... 'git push'" / "As soon as there are no build or test errors create a git tag." / "DO NOT IMPLEMENT PLACEHOLDER OR SIMPLE IMPLEMENTATIONS. WE WANT FULL IMPLEMENTATIONS. DO IT OR I WILL YELL AT YOU"
- Back pressure: "what is hard is ensuring that Ralph has generated the right thing ... Anything can be wired in as back pressure to reject invalid code generation. That could be security scanners, it could be static analysers ... the wheel has got to turn fast." For dynamic languages wire in a type checker or "you will run into a bonfire of outcomes."
- Tests carry their reason: "capture the why tests and the backing implementation is important" — "leaving little notes for future iterations by the LLM, explaining why a test exists".
- `@AGENT.md` "is the heart of the loop. It instructs how Ralph should compile and run the project"; Ralph updates it with learnings.
- Failure modes he names: "the LLM runs ripgrep and comes to the incorrect conclusion that the code has not been implemented" ("If you wake up to find that Ralph is doing multiple implementations ... This nondeterminism is the Achilles' heel of Ralph"); "Claude has the inherent bias to do minimal and placeholder implementations ... the reward function is compiling code"; "you'll wake up to a broken codebase that doesn't compile from time to time"; wrong specs: "my specification for the lexer defined a keyword twice for two opposing scenarios, which resulted in a lot of time wasted"; "Ralph will run out of things to do in the TODO list. Or, it goes completely off track ... I have deleted the TODO list multiple times."
- Tuning, not blaming the tool: "Each time Ralph does something bad, Ralph gets tuned - like a guitar" (the "SLIDE DOWN, DON'T JUMP, LOOK AROUND" sign metaphor). "If Ralph is generating the wrong code or using the wrong technical patterns, then you should update your standard library ... If Ralph is building the wrong thing completely, then your specifications may be incorrect."
- Claims (self-reported, anecdotal): "Ralph can replace the majority of outsourcing at most companies for greenfield projects"; a friend's "$50k USD contract, delivered, MVP, tested + reviewed with @ampcode. $297 USD."; Ralph is building a new language "without that language being in the LLM's training data set". Limits he states: "engineers are still needed. There is no way this is possible without senior expertise guiding Ralph"; "There's no way in heck would I use Ralph in an existing code base"; "This works best as a technique for bootstrapping Greenfield, with the expectation you'll get 90% done with it."
- Maintainability: "When I hear that argument, I question 'by whom'? By humans?"
- CURSED: "i ran Claude in a loop for three months, and it created a genz programming language called cursed"; it has interpreted and compiled modes producing binaries "via LLVM"; "any problems found in cursed can be solved by just running more Ralph loops by skilled operators (ie. people with experience with compilers ...) vs letting Claude just rip unattended" — [ghuntley.com/cursed (2025-09-09)](https://ghuntley.com/cursed/)

**Current Kiro documentation: first-hand vendor material; capability descriptions, not independent effectiveness evidence**
- Feature Specs (page updated **2026-08-04**) now supports Requirements-First and Design-First. - Analyze Requirements (page updated **2026-09-02**) checks interacting requirements for inconsistency, ambiguity, conflicting constraints, unstated assumptions, and missing edge/concurrency cases. Findings arrive as questions naming affected requirements and suggested fixes; answers update `requirements.md`; users can dismiss a question or skip analysis. [Analyze Requirements](https://kiro.dev/docs/specs/analyze-requirements/)
- Correctness (page updated **2026-08-04**) derives properties from EARS requirements in design, links requirement → property → task, generates inputs and shrinks counterexamples during execution. Verbatim: “It provides evidence of correctness, not a proof.” PBT is IDE-only and optional by default. A weak/wrong invariant can pass while actual behavior is wrong; external-service/non-deterministic requirements may need other tests. - Bugfix Specs (page updated **2026-08-04**) separates current defect, expected behavior, and explicitly unchanged behavior. Design investigates root cause; tasks validate reproduction, correction and preserved behavior with PBT. Key regression clause: `THE SYSTEM SHALL CONTINUE TO [existing behavior]`. **Current Spec Kit source: first-hand tool code, pinned 2026-10-14 at `96774bc52fd7dccc7185791e1cac7572b9e09dea`; no code executed**
- The spec template requires prioritized user journeys, each independently testable and useful as an MVP slice; each story has a reason for priority, an **Independent Test**, and Given/When/Then acceptance scenarios. Separate FR identifiers, edge cases, assumptions and measurable, technology-agnostic success criteria record what is wanted. [spec-template, snapshot 2026-10-14](https://github.com/github/spec-kit/blob/96774bc52fd7dccc7185791e1cac7572b9e09dea/templates/spec-template.md)
- The plan template places technical context (language/version, dependencies, storage, testing, target platform, performance, scale and constraints) after the functional spec. It generates research, data model, interface contracts and quickstart; Constitution Check is required before research and again after design. Noncompliance needs explicit complexity/alternative justification. Verbatim gate: “Must pass before Phase 0 research. Re-check after Phase 1 design.” [plan-template, snapshot 2026-10-14](https://github.com/github/spec-kit/blob/96774bc52fd7dccc7185791e1cac7572b9e09dea/templates/plan-template.md)
- `clarify` asks at most five sequential, decision-relevant questions per session, covering functional scope, data, UX, non-functional requirements, integrations, edge cases, constraints and terminology; answers are integrated into the spec. `analyze` then compares spec/plan/tasks for duplication, ambiguity, contradictions, constitution conflict and unmapped requirements, producing location/severity/coverage tables. [clarify, snapshot 2026-10-14](https://github.com/github/spec-kit/blob/96774bc52fd7dccc7185791e1cac7572b9e09dea/templates/commands/clarify.md); [analyze, same snapshot](https://github.com/github/spec-kit/blob/96774bc52fd7dccc7185791e1cac7572b9e09dea/templates/commands/analyze.md)
- The checklist command explicitly says: “Checklists are **UNIT TESTS FOR REQUIREMENTS WRITING**”. They assess completeness, clarity, consistency, measurability and scenario coverage, **not implementation behavior**. Custom checklists are reviewer-owned; `[x]` means that requirement-quality criterion was reviewed as satisfied, not that code is done. The built-in requirements checklist is a separate author-maintained exception. [checklist, snapshot 2026-10-14](https://github.com/github/spec-kit/blob/96774bc52fd7dccc7185791e1cac7572b9e09dea/templates/commands/checklist.md)

Foundational infrastructure precedes stories; each story can then be delivered and tested independently. **Tests are optional in the default:** “Tests are OPTIONAL - only include them if explicitly requested in the feature specification.” If included, they must fail before implementation. [tasks-template, snapshot 2026-10-14](https://github.com/github/spec-kit/blob/96774bc52fd7dccc7185791e1cac7572b9e09dea/templates/tasks-template.md)

### Inferences
- **Inference:** these sources support a shared spec→work→feedback pattern, but not a shared assurance level: a human pause, an agent reviewer and a fault-injected system check examine different things. Similar document names or completion checkboxes cannot establish equivalent delivered behavior. [Reed execution prompt, 2025-05-08](https://harper.blog/2025/05/08/basic-claude-code/); [Superpowers execution choices, snapshot 2026-10-14](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/writing-plans/SKILL.md); [Huntley system verification, 2026-10-13](https://ghuntley.com/agency/)
- **Inference:** skill instructions and executable checks can coexist. Huntley explicitly allows occasional skills while preferring deterministic enforcement; Superpowers combines prescribed skills with test commands. The disagreement concerns reliance and evidence, rather than two mutually exclusive mechanisms.

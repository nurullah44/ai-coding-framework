## Q1. OpenAI "harness engineering": what they built, numbers, golden principles, architecture enforcement, repo legibility, entropy, merge/review flow, failures

### Takeaway
OpenAI's harness-engineering team (3 engineers growing to 7, later described as part of "OpenAI Frontier") built an internal beta product of about 1M lines with zero hand-written code in about 5 months (first commit late August 2025). Quality came from the environment, not from reading code:
- a ~100-line AGENTS.md used as a map into a structured `docs/` system of record;
- a rigid layered architecture (later a 750-package pnpm workspace) checked by custom linters and structural tests whose error messages tell the agent how to fix the problem;
- agent-to-agent review, including security and reliability reviewer agents that run in CI on every push;
- an app, UI, logs, and metrics the agent can read directly;
- an initial weekly "Garbage Collection Day", later supplemented/replaced by recurring cleanup agents that enforce "golden principles".

Their trade-off was minimal blocking merge gates and (by April 2026) no human review before merge, but a human-approved smoke test before release. They say openly that they don't know how the architecture holds up over years. The later public Symphony example includes human approval before merging; these are distinct artifacts and policies, not a single lab-wide merge rule. — [OpenAI, 2026-02-11](https://openai.com/index/harness-engineering/); [Symphony workflow, snapshot 2026-09-15](https://raw.githubusercontent.com/openai/symphony/be10a1b79df723d6d7612b5651c8522704dafb2e/elixir/WORKFLOW.md)

### Cited Findings
**Primary: "Harness engineering: leveraging Codex in an agent-first world", OpenAI, by Ryan Lopopolo, published Feb 11, 2026 (date now verified on the primary page, retrieved 2026-10-14) — https://openai.com/index/harness-engineering/** [P]
- Scope: "building and shipping an internal beta of a software product with **0 lines of manually-written code**." "every line of code—application logic, tests, CI configuration, documentation, observability, and internal tooling—has been written by Codex. We estimate that we built this in about 1/10th the time it would have taken to write the code by hand." — [OpenAI](https://openai.com/index/harness-engineering/)
- Motto: "**Humans steer. Agents execute.**" — [OpenAI](https://openai.com/index/harness-engineering/)
- Start: "The first commit to an empty repository landed in late August 2025." The scaffold (repo structure, CI config, formatting rules, package manager setup, app framework) "was generated by Codex CLI using GPT‑5, guided by a small set of existing templates. Even the initial AGENTS.md file ... was itself written by Codex." — [OpenAI](https://openai.com/index/harness-engineering/)
- Numbers: "the repository contains on the order of a million lines of code ... roughly 1,500 pull requests have been opened and merged with a small team of just three engineers driving Codex. This translates to an average throughput of 3.5 PRs per engineer per day, and surprisingly the throughput has _increased_ as the team has grown to now seven engineers." "the product has been used by hundreds of users internally, including daily internal power users." — [OpenAI](https://openai.com/index/harness-engineering/) [M: self-reported]
- What failed first: "Early progress was slower than we expected, not because Codex was incapable, but because the environment was underspecified. The agent lacked the tools, abstractions, and internal structure required to make progress toward high-level goals." — [OpenAI](https://openai.com/index/harness-engineering/)
- Task splitting: "working depth-first: breaking down larger goals into smaller building blocks (design, code, review, test, etc), prompting the agent to construct those blocks, and using them to unlock more complex tasks. When something failed, the fix was almost never 'try harder.' ... human engineers always stepped into the task and asked: 'what capability is missing, and how do we make it both legible and enforceable for the agent?'" — [OpenAI](https://openai.com/index/harness-engineering/)
- PR / review loop: "we instruct Codex to review its own changes locally, request additional specific agent reviews both locally and in the cloud, respond to any human or agent given feedback, and iterate in a loop until all agent reviewers are satisfied (effectively this is a Ralph Wiggum Loop)." "Humans may review pull requests, but aren't required to. Over time, we've pushed almost all review effort towards being handled agent-to-agent." — [OpenAI](https://openai.com/index/harness-engineering/)
- Bottleneck moved to QA: "As code throughput increased, our bottleneck became human QA capacity." Their fix: "we made the app bootable per git worktree, so Codex could launch and drive one instance per change. We also wired the Chrome DevTools Protocol into the agent runtime and created skills for working with DOM snapshots, screenshots, and navigation." — [OpenAI](https://openai.com/index/harness-engineering/)
- Observability for agents: "Logs, metrics, and traces are exposed to Codex via a local observability stack that's ephemeral for any given worktree ... Agents can query logs with LogQL and metrics with PromQL. With this context available, prompts like 'ensure service startup completes in under 800ms' or 'no span in these four critical user journeys exceeds two seconds' become tractable." "We regularly see single Codex runs work on a single task for upwards of six hours (often while the humans are sleeping)." — [OpenAI](https://openai.com/index/harness-engineering/)
- AGENTS.md as a map: "**give Codex a map, not a 1,000-page instruction manual.**" The "one big AGENTS.md" approach failed: "Context is a scarce resource", "Too much guidance becomes non-guidance", "It rots instantly ... a graveyard of stale rules", "It's hard to verify". "A short AGENTS.md (roughly 100 lines) is injected into context and serves primarily as a map, with pointers to deeper sources of truth elsewhere." — [OpenAI](https://openai.com/index/harness-engineering/)
- Docs as system of record: "The repository's knowledge base lives in a structured docs/ directory treated as the system of record." Design docs are "catalogued and indexed, including verification status and a set of core beliefs"; the architecture doc "provides a top-level map of domains and package layering. A quality document grades each product domain and architectural layer, tracking gaps over time." — [OpenAI](https://openai.com/index/harness-engineering/)
- Plans: "Plans are treated as first-class artifacts. Ephemeral lightweight plans are used for small changes, while complex work is captured in execution plans with progress and decision logs that are checked into the repository. Active plans, completed plans, and known technical debt are all versioned and co-located". (The execution-plan link points to https://cookbook.openai.com/articles/codex_exec_plans.) — [OpenAI](https://openai.com/index/harness-engineering/)
- Mechanical enforcement of docs: "Dedicated linters and CI jobs validate that the knowledge base is up to date, cross-linked, and structured correctly. A recurring 'doc-gardening' agent scans for stale or obsolete documentation that does not reflect the real code behavior and opens fix-up pull requests." — [OpenAI](https://openai.com/index/harness-engineering/)
- Legibility rule: "From the agent's point of view, anything it can't access in-context while running effectively doesn't exist. Knowledge that lives in Google Docs, chat threads, or people's heads are not accessible to the system." "That Slack discussion that aligned the team on an architectural pattern? If it isn't discoverable to the agent, it's illegible". — [OpenAI](https://openai.com/index/harness-engineering/)
- Dependency choice: "Technologies often described as 'boring' tend to be easier for agents to model". Example: instead of a `p-limit`-style package "we implemented our own map-with-concurrency helper: it's tightly integrated with our OpenTelemetry instrumentation, has 100% test coverage". — [OpenAI](https://openai.com/index/harness-engineering/)
- Invariants, not micromanagement: "By enforcing invariants, not micromanaging implementations, we let agents ship fast without undermining the foundation." Example: "we require Codex to parse data shapes at the boundary, but are not prescriptive on how that happens (the model seems to like Zod...)". — [OpenAI](https://openai.com/index/harness-engineering/)
- Layered architecture: "Each business domain is divided into a fixed set of layers, with strictly validated dependency directions and a limited set of permissible edges. These constraints are enforced mechanically via custom linters (Codex-generated, of course!) and structural tests." "code can only depend 'forward' through a fixed set of layers (Types → Config → Repo → Service → Runtime → UI). Cross-cutting concerns (auth, connectors, telemetry, feature flags) enter through a single explicit interface: Providers. Anything else is disallowed and enforced mechanically." "This is the kind of architecture you usually postpone until you have hundreds of engineers. With coding agents, it's an early prerequisite". — [OpenAI](https://openai.com/index/harness-engineering/)
- "Taste invariants" as custom lints: "we statically enforce structured logging, naming conventions for schemas and types, file size limits, and platform-specific reliability requirements with custom lints. Because the lints are custom, we write the error messages to inject remediation instructions into agent context." — [OpenAI](https://openai.com/index/harness-engineering/)
- Rules ladder: "Review comments, refactoring pull requests, and user-facing bugs are captured as documentation updates or encoded directly into tooling. When documentation falls short, we promote the rule into code". — [OpenAI](https://openai.com/index/harness-engineering/)
- Merge philosophy: "The repository operates with minimal blocking merge gates. Pull requests are short-lived. Test flakes are often addressed with follow-up runs rather than blocking progress indefinitely. In a system where agent throughput far exceeds human attention, corrections are cheap, and waiting is expensive. This would be irresponsible in a low-throughput environment." — [OpenAI](https://openai.com/index/harness-engineering/)
- Human role: "We prioritize work, translate user feedback into acceptance criteria, and validate outcomes. When the agent struggles, we treat it as a signal: identify what is missing—tools, guardrails, documentation—and feed it back into the repository, always by having Codex itself write the fix." Agents "often squash and merge their own pull requests." — [OpenAI](https://openai.com/index/harness-engineering/)
- End-to-end autonomy: from one prompt the agent can "Reproduce a reported bug", "Record a video demonstrating the failure", "Implement a fix", "Validate the fix by driving the application", "Record a second video", "Open a pull request", "Respond to agent and human feedback", "Detect and remediate build failures", "Escalate to a human only when judgment is required", "Merge the change". The post's own caveat: "This behavior depends heavily on the specific structure and tooling of this repository and should not be assumed to generalize without similar investment". — [OpenAI](https://openai.com/index/harness-engineering/)
- Entropy: "Codex replicates patterns that already exist in the repository—even uneven or suboptimal ones. Over time, this inevitably leads to drift." "Our team used to spend every Friday (20% of the week) cleaning up 'AI slop.' Unsurprisingly, that didn't scale." — [OpenAI](https://openai.com/index/harness-engineering/)
- Golden principles + garbage collection: "we started encoding what we call 'golden principles' directly into the repository and built a recurring cleanup process." The two examples given: "(1) we prefer shared utility packages over hand-rolled helpers to keep invariants centralized, and (2) we don't probe data 'YOLO-style'—we validate boundaries or rely on typed SDKs". "On a regular cadence, we have a set of background Codex tasks that scan for deviations, update quality grades, and open targeted refactoring pull requests. Most of these can be reviewed in under a minute and automerged." "Human taste is captured once, then enforced continuously on every line of code." — [OpenAI](https://openai.com/index/harness-engineering/)
- Open problems: "What we don't yet know is how architectural coherence evolves over years in a fully agent-generated system." — [OpenAI](https://openai.com/index/harness-engineering/)
- The codebase is also worked on by "other agents (e.g. Aardvark)"; the separate security-agent source is checked below. — [OpenAI](https://openai.com/index/harness-engineering/)

### Inferences
- The quality system is a ladder: a review comment or bug becomes a written rule (docs), then a mechanical check (a custom lint or structural test whose message tells the agent how to fix it), then a reviewer agent or a recurring cleanup agent. Human taste is turned into checks once, then enforced on every change.
- For the described harness loop, completion evidence combines agent review and QA media, and the podcast land skill waits for CI; human approval is at native-app release. This does not establish a universal OpenAI definition of done, or universal blocking CI in the February minimal-gate experiment.
- Low merge gates are a conscious trade-off that the post itself calls "irresponsible in a low-throughput environment". They depend on cheap fixes and strong checks; the primary post also reports external alpha testers, so the earlier "internal-only users" description was wrong. This is an inference about applicability, not evidence that this merge policy fits another team. — [OpenAI, 2026-02-11](https://openai.com/index/harness-engineering/)
- The 1M LOC, 1/10 time, and 3.5 PRs/engineer/day figures are self-reported [M]. No outside audit was found.

## Q2. Anthropic: how the Claude Code team uses Claude Code; AI-written share; how quality is kept; the C compiler (tests, oracles, parallel coordination, limits)

### Takeaway
- **AI-written share:** Claude Code was about 90% written by Claude Code (Sep 2025 interview). Company-wide, more than 80% of code merged at Anthropic in May 2026 was authored by Claude (Anthropic Institute, Jun 4, 2026). The same report says many staff thought Claude's code was worse than human code in late 2025 and "roughly at parity today".
- **Quality practices:** a team CLAUDE.md in git that records mistakes; Plan mode first; giving Claude a way to verify its own work (tests, a browser); formatting hooks; parallel sessions; heavy internal dogfooding.
- **Automated review:** a multi-agent Claude reviewer runs on nearly every PR. Its findings went from 16% to 54% of PRs with substantive comments. It never approves PRs; that stays a human call.
- **Harness research:** Anthropic's harness posts add separate evaluator agents, sprint "contracts" that define done before coding, and JSON feature lists with `passes` flags.
- **C compiler:** a near-perfect test suite plus an oracle (GCC) keeps autonomous agents on track. Near the edge of model ability, agents still broke existing features.

**Anthropic harness research (primary engineering posts)**
- "Effective harnesses for long-running agents" (Justin Young, 2025-11-26). An "initializer agent" sets up "an init.sh script, a claude-progress.txt file ... and an initial git commit". A JSON feature list: "We prompt coding agents to edit this file only by changing the status of a passes field, and we use strongly-worded instructions like 'It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality.'" They chose JSON because "the model is less likely to inappropriately change or overwrite JSON files compared to Markdown files." The agent works "on only one feature at a time". Failure modes: an agent "would look around, see that progress had been made, and declare the job done"; "Claude's tendency to mark a feature as complete without proper testing", fixed by asking it to use browser automation (Puppeteer MCP) "as a human user would". "Clean state" means code "appropriate for merging to a main branch". — [Anthropic, Nov 26, 2025](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) [P]
- "Harness design for long-running application development" (Prithvi Rajasekaran, Labs team, 2026-03-24). Three agents: planner, generator, evaluator. The planner turns "a simple 1-4 sentence prompt" into "a full product spec" and stays at "product context and high level technical design", because spec errors "would cascade into the downstream implementation". — [Anthropic, Mar 24, 2026](https://www.anthropic.com/engineering/harness-design-long-running-apps) [P]
- Sprint contracts define "done" before coding: "the generator and evaluator negotiated a sprint contract: agreeing on what 'done' looked like for that chunk of work before any code was written." "Sprint 3 alone had 27 criteria covering the level editor". The evaluator "used the Playwright MCP to click through the running application the way a user would, testing UI features, API endpoints, and database states"; "Each criterion had a hard threshold, and if any one fell below it, the sprint failed". — [Anthropic, Mar 24, 2026](https://www.anthropic.com/engineering/harness-design-long-running-apps) [P]
- Self-evaluation fails: "agents tend to respond by confidently praising the work—even when, to a human observer, the quality is obviously mediocre." "Out of the box, Claude is a poor QA agent. In early runs, I watched it identify legitimate issues, then talk itself into deciding they weren't a big deal and approve the work anyway." The fix was tuning a separate skeptical evaluator over "several rounds". — [Anthropic, Mar 24, 2026](https://www.anthropic.com/engineering/harness-design-long-running-apps) [P]
- Costs: solo run "20 min | $9" vs full harness "6 hr | $200" ("over 20x more expensive, but the difference in output quality was immediately apparent"); the simplified V2 harness (Opus 4.6) took "3 hr 50 min" and "$124.70". — [Anthropic, Mar 24, 2026](https://www.anthropic.com/engineering/harness-design-long-running-apps) [P]
- Design rule: "every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress testing". "the evaluator is not a fixed yes-or-no decision. It is worth the cost when the task sits beyond what the current model does reliably solo." Even with the planner kept, "Without the planner, the generator under-scoped". — [Anthropic, Mar 24, 2026](https://www.anthropic.com/engineering/harness-design-long-running-apps) [P]

- Change within this experiment: V1 used Opus 4.5 and per-sprint contracts/evaluation; V2, after Opus 4.6, removed the sprint construct and evaluated once at the end while retaining the planner. Independent QA still missed nested bugs and layout/interaction issues after calibration. The original sprint advice is therefore a dated capability workaround, not a permanent prescription. — [Rajasekaran, 2026-03-24](https://www.anthropic.com/engineering/harness-design-long-running-apps) [P]

**C compiler (primary): "Building a C compiler with a team of parallel Claudes", Nicholas Carlini (Safeguards team), Feb 05, 2026 — https://www.anthropic.com/engineering/building-c-compiler** [P]
- Scale: "I tasked 16 agents with writing a Rust-based C compiler, from scratch, capable of compiling the Linux kernel. Over nearly 2,000 Claude Code sessions and $20,000 in API costs, the agent team produced a 100,000-line compiler that can build Linux 6.9 on x86, ARM, and RISC-V." "Opus 4.6 consumed 2 billion input tokens and generated 140 million output tokens", "across two weeks". — [Anthropic, Feb 5, 2026](https://www.anthropic.com/engineering/building-c-compiler)
- Harness: an infinite bash loop running `claude --dangerously-skip-permissions -p "$(cat AGENT_PROMPT.md)"` ("Run this in a container, not your actual machine"). — [Anthropic, Feb 5, 2026](https://www.anthropic.com/engineering/building-c-compiler)
- Coordination: one Docker container per agent and a shared bare git repo. "Claude takes a 'lock' on a task by writing a text file to current_tasks/ ... If two agents try to claim the same task, git's synchronization forces the second agent to pick a different one." "Merge conflicts are frequent, but Claude is smart enough to figure that out." "I don't use an orchestration agent." — [Anthropic, Feb 5, 2026](https://www.anthropic.com/engineering/building-c-compiler)
- Tests as the main control: "it's important that the task verifier is nearly perfect, otherwise Claude will solve the wrong problem." "near the end of the project, Claude started to frequently break existing functionality each time it implemented a new feature. To address this, I built a continuous integration pipeline and implemented stricter enforcement ... so that new commits can't break existing code." — [Anthropic, Feb 5, 2026](https://www.anthropic.com/engineering/building-c-compiler)
- Tests written for the agent: short output ("At most, it should print a few lines of output and log all important information to a file"); "ERROR" and the reason on the same line so grep finds it; pre-computed summary statistics; a "--fast option that runs a 1% or 10% random sample", "deterministic per-agent but random across VMs"; agents keep "extensive READMEs and progress files". — [Anthropic, Feb 5, 2026](https://www.anthropic.com/engineering/building-c-compiler)
- Oracle: when all 16 agents got stuck on the same Linux kernel bug, "The fix was to use GCC as an online known-good compiler oracle to compare against", compiling a random part of the kernel with GCC and the rest with Claude's compiler, plus "delta debugging techniques to find pairs of files that failed together but worked independently." — [Anthropic, Feb 5, 2026](https://www.anthropic.com/engineering/building-c-compiler)
- Role agents for quality: "LLM-written code frequently re-implements existing functionality, so I tasked one agent with coalescing any duplicate code it found." Other agents covered compiler performance, output code efficiency, a Rust-developer design critique ("make structural changes ... to improve the overall code quality"), and documentation. — [Anthropic, Feb 5, 2026](https://www.anthropic.com/engineering/building-c-compiler)
- Spec: "a from-scratch optimizing compiler with no dependencies, GCC-compatible, able to compile the Linux kernel, and designed to support multiple backends. While I specified some aspects of the design (e.g., that it should have an SSA IR to enable multiple optimization passes) I did not go into any detail on how to do so." — [Anthropic, Feb 5, 2026](https://www.anthropic.com/engineering/building-c-compiler)
- Results and limits: "99% pass rate on most compiler test suites including the GCC torture test suite"; it builds QEMU, FFmpeg, SQLite, Postgres, Redis, and runs Doom. Limits:
  - no 16-bit x86 code generator ("Claude simply cheats here and calls out to GCC");
  - its assembler and linker were then "still somewhat buggy";
  - "not yet a drop-in replacement";
  - "less efficient code than GCC with all optimizations disabled";
  - "The Rust code quality is reasonable, but is nowhere near the quality of what an expert Rust programmer might produce";
  - "New features and bugfixes frequently broke existing functionality."
  — [Anthropic, Feb 5, 2026](https://www.anthropic.com/engineering/building-c-compiler)
- Author's warning: "it is easy to see tests pass and assume the job is done, when this is rarely the case. I used to work in penetration testing ... the thought of programmers deploying software they've never personally verified is a real concern." — [Anthropic, Feb 5, 2026](https://www.anthropic.com/engineering/building-c-compiler)

## Q4. Lens across labs: project stages, specs/plans, task splitting, definition of "done", small models doing coding, reviewers/QA catching misses

### Takeaway
- **Specs and plans:** OpenAI's harness team checks ExecPlans (milestones + acceptance criteria) into the repo, and Lopopolo wants any governing plan reviewed line by line as its own PR. Boris iterates in Plan mode until the plan is good. Anthropic's long-running harnesses use a planner agent that writes a high-level product spec. Carlini wrote a short goal spec plus tests.
- **Task splitting:** OpenAI goes depth-first into building blocks. Anthropic harnesses do one feature at a time from a JSON list, or sprints. Carlini used lock files and one failing test per agent.
- **"Done":** defined by machine checks (tests, oracle, driving the app, contracts with hard thresholds, QA-plan evidence, agent reviewers satisfied). Humans validate outcomes, approve at Anthropic, and approve the smoke test at release at OpenAI.
- **Small models:** the OpenAI harness started on Codex Mini, but practitioners prefer the top model (Boris: Opus over the smaller model). OpenAI's Codex team trained a dedicated review model. Haiku is documented for a commit helper in the October 2025 interview; main production implementation on small models is not established by these sources.

## Q5. Coverage of architecture, system design, and layers (app, security, network): who addresses it, with what examples

### Takeaway
- **App architecture:** OpenAI's harness team is the most concrete. It uses fixed per-domain layers with forward-only dependencies, enforced by linters and structural tests; cross-cutting concerns (auth, connectors, telemetry, feature flags) enter only through "Providers"; the result was a 750-package pnpm workspace.
- **Security:** OpenAI runs security and reliability reviewer agents in CI, plus a security skill and Aardvark. Anthropic's automated reviewer looks for "security flaws" and once caught an auth-breaking one-line change. Codex sandboxes network and filesystem by default. Claude Code's permission system is its most complex part.
- **Network:** the one concrete network-layer rule found is OpenAI's reviewer check for "timeouts and retries on this bit of network code".
- **System design (Claude Code team):** "simplest possible option", a thin shell around the model.

### Cited Findings
- OpenAI layered rule (Types → Config → Repo → Service → Runtime → UI; Providers for auth, connectors, telemetry, feature flags), plus custom lints for structured logging, schema naming, file size limits, and "platform-specific reliability requirements". — [OpenAI, Feb 2026](https://openai.com/index/harness-engineering/)
- "750 packages in the pnpm workspace, isolated by business logic domain or layer of the stack". — [AI Engineer talk, 34:31](https://www.youtube.com/watch?v=am_oeAoUhew&t=2071s)
- Network/reliability review in CI: "are there timeouts and retries on this bit of network code?" — [AI Engineer talk, 12:09](https://www.youtube.com/watch?v=am_oeAoUhew&t=729s); production data safety: "making sure that we don't have any PII leaking in the logs in production" — [AI Engineer talk, 45:07](https://www.youtube.com/watch?v=am_oeAoUhew&t=2707s)
- Codex: the sandbox "restricts network access and filesystem access by default"; a "Security best-practices skill"; Fouad Matin "is responsible for Codex's safety and security approach". — [Pragmatic Engineer, Feb 17, 2026](https://newsletter.pragmaticengineer.com/p/how-codex-is-built) [S]
- Anthropic: the automated Claude reviewer "looks for bugs, security flaws, and other defects before it can merge" — [Anthropic Institute, Jun 4, 2026](https://www.anthropic.com/institute/recursive-self-improvement); a flagged one-line change "would have broken authentication for the service" — [Claude blog, Mar 9, 2026](https://claude.com/blog/code-review)
- Claude Code: a permission system with static analysis of commands against a multi-tier settings file (project, user, company); runs locally without virtualization for simplicity. — [Pragmatic Engineer, Sep 23, 2025](https://newsletter.pragmaticengineer.com/p/how-claude-code-is-built) [S]
- C compiler: the human specified only top-level design (SSA IR, multiple backends); a dedicated agent critiqued the design "from the perspective of a Rust developer". — [Anthropic, Feb 5, 2026](https://www.anthropic.com/engineering/building-c-compiler)

### Inferences
- Explicit architecture rules appear where agents work with little human review (the OpenAI harness, the compiler's critique agent). The Anthropic sources stress human approval responsibility, review agents and permissions; they do not establish an audited fraction of all PRs approved by humans. Do not infer that lab-wide architectural rules are absent.

### Gaps
- No lab source gives a full threat model, network-segmentation rules, or infrastructure-layer design rules for agent-written code. Only the examples above were found.

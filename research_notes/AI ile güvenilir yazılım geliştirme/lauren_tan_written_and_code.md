## 1. pstack (cursor/plugins, folder pstack): what it is, its full structure, what each part does, and the principles it states

### Takeaway
pstack is Lauren Tan's MIT-licensed Cursor plugin. The first commit was 2026-05-23 and the version on 2026-10-13 was 0.15.23. It packages her personal agent workflow as 53 skill folders (29 workflow skills plus 24 one-principle skills), 2 subagents, a 10-chapter guide, a dormant "benny" Slack automation pack and a few scripts. It ships no hooks, no `commands/` folder and no static rules. The only rule is generated at setup time. The core is `/poteto-mode`, a router that copies the steps of one of 23 playbooks verbatim into the todo list. The design centres on three ideas: verify against the real artifact, enforce through structure (scripts, lints, types) rather than prose, and "no planning skill" (you plan through code and prototypes).

#### Benny: complete automation pack and gates (first-hand repo material, snapshot 2026-10-13)

- **Setup and refresh:** merge into `.cursor/automations/benny/`, preserve destination-only files and local edits, keep user configuration/maps outside that directory, and enable shared pstack skills in committed `.cursor/settings.json`. A fresh agent in the target repo must resolve dependencies; a skill already loaded in the installing session is insufficient. The source says, "Do not create or update an automation until the user explicitly asks." The setup source is being studied here, not invoked. — [setup-benny, snapshot 2026-10-13](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/automations/benny/skills/setup-benny/SKILL.md)
- **Triage:** read the exact source thread and attachments; classify bug/performance, feature request, question/feedback or reroute; trace the owning layer and recent history; dedupe using error signature, area, trigger, symptom, version and source link. Create only a clear live net-new bug/performance issue. "For a possible match, link it in the verdict as uncertain and create nothing." Post exactly one thread reply with `[benny:bug]`, `[benny:performance]` or `[benny:other]`, then read it back. If a new tracker issue exists but the handoff failed, compensate by canceling/closing/deleting that issue and verify compensation. — [triage-issue-reports, snapshot 2026-10-13](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/automations/benny/skills/triage-issue-reports/SKILL.md)
- **Tracker and ticket contract:** "The tracker is an adapter, not a required vendor. A Linear adapter is one valid example. A GitHub Issues adapter or another tracker may implement the same contract." The adapter must search/read/create/update/link and compensate. "The new issue must be self-contained": area/symptom title, reporter quote, expected and observed behavior, version/environment or `unknown`, trigger/frequency, source permalink, cause findings with hypotheses labeled, representative media, remaining artifact links, configured status/labels. "Do not put a guessed root cause in the title." This corrects the earlier notes' blanket statement that pstack gives no external-ticket guidance; feature-development briefs remain separate from this bug-intake contract. — [triage-issue-reports, snapshot 2026-10-13](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/automations/benny/skills/triage-issue-reports/SKILL.md)
- **Reproduction and done:** accept the verdict only from the configured identity in the original thread; stop if a human owns the fix; inspect and verify an existing PR/commit rather than authoring a competing fix. Require real UI control, read-only inspection, screenshots, recording and cleanup. Name the correct and broken states, reach the discriminating state twice with independent resets, cross-check stored state, and have a read-only media reviewer check that the evidence actually shows the symptom. `Could not reproduce` and `Blocked` are useful outcomes. — [reproduce-and-fix-issues, snapshot 2026-10-13](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/automations/benny/skills/reproduce-and-fix-issues/SKILL.md)
- **Fix gate and review:** retain baseline evidence, repeat the identical real UI path twice after the patch, prove both removal of the broken state and presence of the expected state, capture after media and the same state cross-check, run focused tests and nearby blast-radius flows. "A compile, unit test, code review, or plausible diff is not after evidence." Only then run required repo checks and open a small draft PR with root cause and before/after evidence. "Never merge or deploy from this workflow." — [reproduce-and-fix-issues, snapshot 2026-10-13](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/automations/benny/skills/reproduce-and-fix-issues/SKILL.md)
- **Security and network boundary:** freeze channel/thread coordinates; the coordinator alone posts; read-only analysis children get no Slack credentials/write tools; a code worker edits only in an environment that provably excludes Slack credentials and write capabilities. Missing configuration, feature coverage or adapter capabilities stops the run. The YAML example includes explicit model slots, thread-only flags, tracker compensation, draft-only PRs, temporary artifact retention and bounded polling/repro/fix budgets. This is concrete automation isolation, not a general application-security or network-architecture blueprint. — [FOR_AGENTS.md](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/automations/benny/FOR_AGENTS.md), [configuration.example.yaml](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/automations/benny/templates/configuration.example.yaml), both snapshot 2026-10-13

### Takeaway

#### "The Complete Guide to pstack Pt. 2" (X Article, 2026-09-09; her words)
Source for every quote in this sub-section: [x.com/poteto/status/2097732320606507506](https://x.com/poteto/status/2097732320606507506) (article https://x.com/i/article/2094940651607715840). Engagement on 2026-10-14 was 3,774 likes and ~621K views.
- "if an agent can't verify its own work, nothing else matters. You remain the bottleneck, and your whole day will be spent babysitting your agents."
- Two failure modes: "They are unable to fully understand your intent because they're under/poorly specified." "They don't have enough context on how to do the work correctly." "Using agents well comes down to how well you're able to prime the agent's context window with high quality context."
- "the latest models are able to write code better than you or I can... This is the art of supervising someone smarter than you, on a codebase you haven't written yourself, and where humans can no longer fit the entire mental model of the codebase in their head."
- The indirect prompt: "Instead of telling the agent exactly what I want, I try to draw it out of the agent instead - in its own words." Its three benefits: it compresses noise into a problem statement, it lets her "catch misunderstandings immediately", and "I haven't potentially led it down the wrong path by stating my own assumptions".
- Context from history: "your past transcripts are often a gold mine for rich context" (`/recall`). `/why` "queries historical evidence across multiple sources in parallel: Git history and PR review comments, Linear tickets, Notion design docs, Slack conversations, Datadog monitors, Sentry errors, code lineage, and analytics warehouse events."
- Agents overclaiming: "they still often state things confidently without backing it up with data or actually reading the code needed to build up a mental model of how it works. So this act of teaching you what it's going to do and why ends up helping the agent too."
- Planning: "most harnesses that have plan modes tend to over-specify implementation details and under-specify everything else. That's why in pstack, I cheekily said that 'I don't believe in planning'. The truth is that I do plan, but I do so through code."
- README-driven development: "I am a big believer in readme driven development." For Dune ("our in-house client framework for desktop apps") she "started by first writing a tutorial for it". She created `/technical-writing` because the first README "tried to be a tutorial, a how-to guide, an architectural explanation, and an API reference all in the same document".
- "Writing a plan this way is very helpful because it also gives your agents a concrete target and goal that it can check its own work against."
- "two of the most common mistakes I see are: Accepting the agent's first design. Overcooking the plan without empirical evidence." "Prototyping is planning, but with code."
- Her role: "As an engineer in the agentic era, it's more important to spend my time on architecture, choosing the right data structures, and thinking about how the systems I build will work together. My agents fill in the implementation details."
- Architect: "Each runner must evaluate interface depth, examine failure modes on weak models, and screen against our catalog of design red flags." "If the same workaround appears across unrelated call sites, or if the types require escape hatches like `any` or forced casts, that is empirical proof that the architecture is wrong."
- "I never bother with reviewing abstract plans adversarially. The agents start hallucinating theoretical risks, and inventing complex edge cases to protect against problems that will never happen."
- On plans: "Every single task in the plan is structured around proof and verification. The playbook tells agents that tests alone are not sufficient verification." "Every plan is checked by an automated script that validates its structure and formatting. Once approved, the plan executes item by item. Each PR is small, self-contained, and easily reviewed." "commit the plans temporarily to the codebase so that other agents are aware of the work in progress. But I typically delete them when I'm done... I don't find it valuable to keep plans around permanently."
- "Plan Mode is often used as a way to convince yourself that the agent is going to do the right thing. But the reality is that abstract plans only give you the illusion of progress."

#### Agents copy patterns, architecture and layers (her words, in pstack code)
- "Assume every contributor is an agent that sees only the files it opened, copies the nearest example, and takes the shortest path that compiles. Design the repo so a change that looks right from one file is right for the whole repo." (Added 2026-10-03.) — [correct/SKILL.md](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/skills/correct/SKILL.md)
- `/correct` ladder: "1. **Eliminate it with architecture.** Give each piece of state one owner and each task one supported way. Hide internals so the wrong import fails. Replace hand-synced lists with one source of truth. Delete old ways and dead code an agent would copy. 2. **Enforce it with types**... If bad code still compiles, add a lint or CI check whose error names the file, type, or function to use instead. If the pattern is already common, fail only when a change adds more. 3. **Test the behavior.** 4. **Write docs or agent rules last, only for judgment calls.** Nothing fails when an agent skips them." Also: "Prove each new check fails on a real past mistake." "Exceptions go on the offending line with a reason, an expiry date, and a human's approval." "keep a table in the agent instruction file that pairs each rule with what enforces it." — [correct/SKILL.md](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/skills/correct/SKILL.md)
- Guide version of the same ladder: "Human review isn't on the list. A reviewer who must catch the same mistake on every PR is the problem this fixes." — [guide ch. 9](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/docs/guide/09-make-it-yours.md)
- Design red flags (added 2026-10-03). Source: [architect/references/design-red-flags.md](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/skills/architect/references/design-red-flags.md)
  - "**Two ways to do one task**... An agent copies whichever way it finds first, so every way keeps gaining callers. Keep one way."
  - "**Importable internals**... An agent takes the shortest path that compiles, so it imports them directly... Make internals unreachable from outside the module, so an import from outside fails the build."
  - "**Hand-synced list**... An agent that sees one list updates only that one... If a list can't be derived, make the build fail when the lists disagree."
  - "**Split ownership**... An agent that edits one writer can't see the others, so their rules diverge."
  - Other flags: shallow module, information leakage, temporal decomposition and pass-through method.
- Architect Phase B: "Assume the next contributor is an agent that sees only the files it opened, copies the nearest example, and takes the shortest path that compiles. Prefer the design where a change that looks right from one file is right for the whole repo." — [architect/SKILL.md](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/skills/architect/SKILL.md)
- Code-quality lens used by `/interrogate`. Source: [interrogate/references/code-quality-review.md](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/skills/interrogate/references/code-quality-review.md)
  - "Do not let a PR push a file from under 1k lines to over 1k lines without a very strong reason."
  - "Treat 'weird if statements in random places' as a design problem, not a style nit."
  - "Keep logic in the canonical layer and reuse existing helpers."
  - It looks for "code judo" moves, defined as "restructurings that preserve behavior while making the implementation dramatically simpler".

## 5. How her material handles project stages, writing and checking specs, splitting work into tickets, and defining "done" (for a small model to follow and a reviewer to catch misses)

### Takeaway
Her material replaces up-front prose specs with three things. First, a prompt that states the goal, a pass/fail "done check", the proof wanted, known facts and real constraints. Second, executable targets: prototypes, a README or tutorial written first, usage-first type sketches, and characterization pins. Third, and only after the design settles, a machine-checked plan where each PR is one unit. Each unit lists its files, one build step, one observable result, unit/live/perf verification boxes (live lanes name a screenshot path and a "Pass when" predicate), a review gate and merge conditions.

Delegated work goes out as a brief with GOAL / SCOPE / CONTEXT / ACCEPTANCE / VERIFY / TIMEBOX / FORBIDDEN / REPORT fields, and "Missing fields are a refuse-to-spawn condition."

"Done" is a falsifiable predicate checked on the real artifact by an agent that did not write the code. Inconclusive is not a pass, and CI green is not a verdict.

### Inferences
- For a team using cheap coding models, the most transferable pieces are, in my reading:
  1. The five-part prompt with a pass/fail done check.
  2. The GOAL…REPORT brief with refuse-to-spawn on missing fields.
  3. The per-PR plan skeleton plus a linter like `check-plan.mjs`.
  4. A verification skill with a feature map.
  5. An independent verifier's verdict recorded per head SHA, where CI green is not a verdict and inconclusive is not a pass.
  6. The `/correct` ladder, which moves repeated review comments into architecture, types or lint.
- The "don't believe in planning" stance and the very heavy plan template (ten live lanes per PR) are reconciled by sequencing and scope. The plan comes only after prototypes settle the design, and it is skipped for one- or two-file changes.
- The ten-lane, screenshot-and-video bar assumes cloud VMs and abundant tokens. She acknowledges abundant tokens only in the third-party Maven summary (that she works at an AI lab with near-unlimited tokens), not in her own written words found so far. A small team would need to scale this down; Orchestrate itself says "Size the brief to the unit."

## Q1. Inventory of every skill in mattpocock/skills: purpose, inputs, outputs, where each stops; how they define a good spec, a good ticket, and "done"; is it simple enough for a small model?

### Takeaway
The repo holds 38 skills: 27 "promoted" ones that ship in the plugin (engineering + productivity), 4 frozen `misc/` skills, 7 beta `in-progress/` skills, and an empty `deprecated/` bucket. The main flow is `/grill-with-docs` → (optional `/prototype`) → `/to-spec` → `/to-tickets` → `/implement` (or `/implement-spec`), which drives `/tdd` and `/code-review` → `/pr` → `/retro`. Outputs include Markdown glossary/ADRs, spec and ticket issues or `.scratch/` files, a temporary HTML architecture report, and PR bodies. `triage` supplies the most explicit acceptance-criteria quality rules; `to-spec` has no separate acceptance-criteria section. `implement` requires typechecking, tests, review and commit, but no universal running-app proof gate. **Correction:** runtime checks are available in diagnosis and were used in Matt's July demo; the earlier blanket statement that nothing in the flow checks a running artifact was too strong. — [README, source version 2026-10-09](https://github.com/mattpocock/skills/blob/49dd158/README.md); [router](https://github.com/mattpocock/skills/blob/49dd158/skills/engineering/ask-matt/SKILL.md); [implement](https://github.com/mattpocock/skills/blob/49dd158/skills/engineering/implement/SKILL.md); [tutorial, 2026-07-16, 14:58–15:10](https://www.youtube.com/watch?v=M6mYodf0dJM&t=898s)

**The main flow, as Matt's router defines it [1st]** — [ask-matt/SKILL.md](https://github.com/mattpocock/skills/blob/49dd158/skills/engineering/ask-matt/SKILL.md)
- "1. **`/grill-with-docs`** sharpens the idea by interview. Start here whenever you are **working in a working directory**: it's stateful, retaining what it learns in `GLOSSARY.md` and ADRs."
- "2. **Branch: can you settle every question in conversation?** If a question needs a runnable answer (state, business logic, a UI you have to see), detour through a prototype, bridged by **`/handoff`** in both directions"
- "3. **Branch: is this a multi-session build?** **Yes** → **`/to-spec`** (turn the thread into a spec), then **`/to-tickets`** ... Then work the tickets one of two ways: **`/implement`** per ticket, **`/clear`ing context between each one** ... **`/implement-spec`** for the whole spec in one run." "**No** → **`/implement`** right here, in the same context window."
- "Either way, the code gets built by driving **`/tdd`** (one red-green slice at a time) and closes out with **`/code-review`**, a two-axis review (Standards + Spec) of the diff."
- "When the work goes up as a pull request, **`/pr`** shapes the body"
- "4. **`/retro`** closes the loop. ... it looks back over the session and suggests changes to the agent's **environment**, not the code ... Mechanical mistakes become deterministic checks; judgement calls become coding standards."
- On-ramps: "**Bugs and requests piling up** → **`/triage`**", "**Something's broken** → **`/diagnosing-bugs`**", "**A huge, foggy effort** ... → **`/wayfinder`**". "Triage is only for issues **you didn't create** ... Tickets that `/to-tickets` produced are already agent-ready, so **don't triage them**."
- Context hygiene: "Keep steps 1–3 in **one unbroken context window** (don't compact or clear until after `/to-tickets`)". The limit is the "**smart zone**: the window (~150k tokens on state-of-the-art models) within which the model still reasons sharply."
- Precondition: "**`/setup-matt-pocock-skills`**: run before your first engineering flow".

6. **to-spec** (formerly to-prd) — "Turn the current conversation into a spec and publish it to the project issue tracker: no interview, just synthesis of what you've already discussed." "Do NOT interview the user; just synthesize what you already know." Step 2: "Sketch out the seams at which you're going to test the feature. Existing seams should be preferred to new ones. Use the highest seam possible. ... the ideal number is one. Check with the user that these seams match their expectations." Step 3: publish and "Apply the `ready-for-agent` triage label". Template sections: **Problem Statement**, **Solution** (both "from the user's perspective"), **User Stories** ("A LONG, numbered list ... As an <actor>, I want a <feature>, so that <benefit> ... extremely extensive"), **Implementation Decisions** (modules, interfaces, "Architectural decisions", "Schema changes", "API contracts"; "Do NOT include specific file paths or code snippets"), **Testing Decisions** ("only test external behavior, not implementation details", modules to test, prior art), **Out of Scope**, **Further Notes** — [SKILL.md](https://github.com/mattpocock/skills/blob/49dd158/skills/engineering/to-spec/SKILL.md)
7. **to-tickets** (merged from to-plan + to-issues) — "Break a plan, spec, or the current conversation into a set of tracer-bullet tickets, each declaring its blocking edges". Slice rules: "Each slice cuts a narrow but COMPLETE path through every layer (schema, API, UI, tests): vertical, NOT a horizontal slice of one layer", "A completed slice is demoable or verifiable on its own", "Each slice is sized to fit in a single fresh context window", "Any prefactoring should be done first". Wide refactors are sequenced "as **expand–contract**". Step 4 "Quiz the user" ("Iterate until the user approves the breakdown"). Output: one local file per ticket, or one tracker issue per ticket with native blocking links and the `ready-for-agent` label. Template fields: "**What to build:** the end-to-end behaviour this ticket makes work, from the user's perspective", "**Blocked by:**", "**Status:** ready-for-agent", "- [ ] Acceptance criterion 1". "Do NOT close or modify any parent issue." — [SKILL.md](https://github.com/mattpocock/skills/blob/49dd158/skills/engineering/to-tickets/SKILL.md)
8. **implement** — "Implement a piece of work based on a spec or set of tickets." Implementation instructions include: "Call the Skill tool with "tdd" where possible, at pre-agreed seams. Run typechecking regularly, single test files regularly, and the full test suite once at the end. Once done, call the Skill tool with "code-review" to review the work. 9. **implement-spec** — "Implement the result of /to-spec and /to-tickets in code."

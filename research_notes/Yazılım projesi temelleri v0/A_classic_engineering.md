# A — Classic engineering foundations for a small web product

Retrieved: **2026-10-16**. Scope: manual engineering, v0, approximately 0–5,000 users. Search queries used: **18**; other source pages were opened directly. No video claims.

Evidence rule: an author's recommendation is attributed, not treated as a benchmark or universal rule. Adoption costs below are the work the source describes; money/time estimates are **Not in sources** unless stated. An exact 5,000-user cutoff is **Not in sources** unless stated.

The options are not always exclusive: a delivery method can use ADRs, a monolith can be modular, and SLOs can use existing monitoring. The comparisons below preserve those relationships. [Nygard](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions), [Shopify](https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity), [Google SRE](https://sre.google/workbook/implementing-slos/)

## 1. Project phases and architecture documentation

| Option; what it is; who recommends it | When it fits / when it does not | Adoption cost |
|---|---|---|
| **Design doc before implementation.** Malte Ubl describes Google's informal document: context, goals/non-goals, design, alternatives and cross-cutting concerns. The lifecycle is draft/review → implementation and iteration → maintenance and learning. [Ubl, 2020](https://www.industrialempathy.com/posts/design-docs-at-google/) | Fits ambiguous designs needing trade-off discussion or agreement. Little value for an obvious implementation; review overhead can hinder rapid prototyping. [Ubl](https://www.industrialempathy.com/posts/design-docs-at-google/) | Writing, review and updates. A mini doc can be 1–3 pages; larger projects often use 10–20. [Ubl](https://www.industrialempathy.com/posts/design-docs-at-google/) |
| **Shape Up: shape → bet → build.** Define a bounded problem/solution, commit a limited amount of time, then let the team build. Ryan Singer/Basecamp distinguish exploratory R&D, production and cleanup for a new product. [New products](https://basecamp.com/shapeup/2.3-chapter-09) | For two or three people, the same people can alternate shaping and building; formal pitches, betting meetings, six-week cycles and cooldowns can be dropped. More specialized teams benefit from the structure. [Adjust to your size](https://basecamp.com/shapeup/4.1-appendix-02) | Deliberate shaping and time limits still remain. Formal cycles require uninterrupted building time and people doing shaping outside those cycles. [Size](https://basecamp.com/shapeup/4.1-appendix-02), [bets](https://basecamp.com/shapeup/2.2-chapter-08) |
| **Lightweight architecture record.** Nygard's ADR records one significant decision: context, decision, status and consequences. C4 supplies diagrams; arc42 supplies a broader documentation template. These are documentation tools, not a complete delivery process. [Nygard, 2011](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions), [C4](https://c4model.com/diagrams), [arc42](https://arc42.org/overview/) | ADRs fit decisions about structure, quality, dependencies and interfaces; decisions need not all happen at project start. C4 says context/container diagrams suffice for most teams; use other levels only when valuable. arc42 is tailorable and offers a one-page canvas. [Nygard](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions), [C4](https://c4model.com/diagrams), [arc42](https://arc42.org/overview/) | Nygard proposes 1–2 pages per decision in version control; retain superseded records. Diagrams/template sections require creation and maintenance; fixed time estimates are **Not in sources**. [Nygard](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions), [C4](https://c4model.com/diagrams), [arc42](https://arc42.org/overview/) |

**Where architecture sits:** Ubl's document uses goals/requirements to compare solutions before coding; it is not itself a requirements document, and changes during implementation feed back into it. Shape Up explicitly allows building exploratory pieces before the new product's architecture is settled. A universal spec → architecture → tickets sequence is **Not in sources**. [Ubl](https://www.industrialempathy.com/posts/design-docs-at-google/), [Basecamp R&D/production](https://basecamp.com/shapeup/2.3-chapter-09)

**Tickets:** Shape Up hands a whole project to the builders; they discover and define tasks during implementation. It explicitly rejects an architect splitting all work into assigned tasks beforehand. ADRs likewise capture decisions throughout a project, not only at its beginning. [Basecamp, handover](https://basecamp.com/shapeup/3.1-chapter-10), [Nygard](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)

**Terminology:** a C4 “container” means a running application or data store; it does not require Docker. [C4 definition](https://c4model.com/abstractions/container)

**Small-product recommendation in these sources:** Basecamp explicitly reduces ceremony for tiny teams. Ubl recommends choosing documentation by ambiguity and review value, rather than documenting every change. Neither sets a user-count threshold. [Basecamp](https://basecamp.com/shapeup/4.1-appendix-02), [Ubl](https://www.industrialempathy.com/posts/design-docs-at-google/)

## 2. Architecture style

| Option; what it is; who recommends it | When it fits / when it does not | Adoption cost |
|---|---|---|
| **Monolith first / majestic monolith.** One application contains the product's behavior. Fowler argues for beginning with a monolith; DHH says most web apps should start and can remain this way. [Fowler, 2015](https://martinfowler.com/bliki/MonolithFirst.html), [DHH, 2020](https://signalvnoise.com/svn3/the-majestic-monolith-can-become-the-citadel/) | Fits simple/new products. DHH proposes extracting a specialized outpost only after attempts to improve the monolith fail, for divergent load, implementation or organizational needs. [DHH](https://signalvnoise.com/svn3/the-majestic-monolith-can-become-the-citadel/) | One test/deploy pipeline and shared database reduce overhead. Unrestricted coupling can later make changes fragile. [Shopify, 2019](https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity) |
| **Modular monolith.** One deployed application, with boundaries between business domains. Shopify chose it to improve modularity without multiplying deployment units. [Shopify](https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity) | Fits a monolith whose coupling impedes development. Shopify cautions against weeks/months of architecture for an unknown early system. [Shopify](https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity) | Define public interfaces, data ownership and dependency rules, then enforce them. Shopify's later account stresses grouping code that changes together, not merely drawing boundaries. [2019](https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity), [2020 lessons](https://shopify.engineering/shopify-monolith) |
| **Microservices / independent subsystems first.** Stefan Tilkov argues for separate delivery boundaries when independent parallel development is the goal and the domain is already well understood. [Tilkov, 2015](https://martinfowler.com/articles/dont-start-monolith.html) | Tilkov explicitly exempts a possible two-developer, few-week build and favors known domains/replacements. Fowler advises against starting here without team experience. [Tilkov](https://martinfowler.com/articles/dont-start-monolith.html), [Fowler](https://martinfowler.com/bliki/MonolithFirst.html) | Multiple pipelines, infrastructure and network failure modes; changing service boundaries is harder. [Shopify](https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity), [Tilkov](https://martinfowler.com/articles/dont-start-monolith.html) |

**Small-product recommendation:** DHH favors a monolith for most web apps; Shopify favors little early architecture, then investment as development slows. Fowler's support is explicitly tentative/anecdotal, not a controlled result; he warns that arbitrary monoliths cannot simply be split later. No source guarantees growth without a rewrite or uses 5,000 users as the decision boundary. [DHH](https://signalvnoise.com/svn3/the-majestic-monolith-can-become-the-citadel/), [Shopify](https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity), [Fowler](https://martinfowler.com/bliki/MonolithFirst.html)

**Disagreement:** Tilkov disputes monolith-first when separate services are the intended destination, because extraction can be very hard. He still says distribution needs a strong reason and a well-structured monolith may never need it. This is not unanimous advice to adopt microservices. [Tilkov](https://martinfowler.com/articles/dont-start-monolith.html)

## 3. Technology choice and moving parts

| Option; what it is; who recommends it | When it fits / when it does not | Adoption cost |
|---|---|---|
| **Reuse a small mature toolkit.** Dan McKinley favors understood capabilities/failure modes and whole-system choices. [Choose Boring Technology, 2015](https://mcfunley.com/choose-boring-technology) | Fits when technology novelty is not the product's value. Old does not automatically mean good. [McKinley](https://mcfunley.com/choose-boring-technology) | Each added tool brings operations, monitoring, testing and learning work. [McKinley](https://mcfunley.com/choose-boring-technology) |
| **Add a specialized/new tool deliberately.** McKinley permits additions after examining how the existing stack could solve the problem and why that would be too costly. [McKinley](https://mcfunley.com/choose-boring-technology) | Fits a benefit that survives organization-wide cost review; enthusiasm alone is insufficient. [McKinley](https://mcfunley.com/choose-boring-technology) | More unknown failure modes and operations; overlapping tools also need a migration plan. His approximate three innovation tokens describe limited attention, not a three-service limit. [McKinley](https://mcfunley.com/choose-boring-technology) |

**Small-product recommendation:** McKinley favors a bias toward mature tools and fewer additions. A prescribed v0 count of languages, services or databases is **Not in sources**. His 2015 examples are historical examples, not a current ranking. [McKinley](https://mcfunley.com/choose-boring-technology)

## 4. Scaling readiness

| Option; what it is; who recommends it | When it fits / when it does not | Adoption cost |
|---|---|---|
| **Keep a relational database; increase its capacity first.** AWS describes adding CPU/memory/network capacity as a common first scaling step that preserves the application's architecture. [AWS, 2024](https://aws.amazon.com/blogs/database/scale-your-relational-database-for-saas-part-1-common-scaling-patterns/) | Fits until instance/resource limits or workload constraints intervene. AWS also identifies indexing and data-model improvements as alternatives. It does not prescribe one database for every small product. [AWS](https://aws.amazon.com/blogs/database/scale-your-relational-database-for-saas-part-1-common-scaling-patterns/) | Larger infrastructure bill; ordinary RDS instance resizing restarts the database. Managed databases offload generic administration. [Scaling](https://aws.amazon.com/blogs/database/scale-your-relational-database-for-saas-part-1-common-scaling-patterns/), [AWS startup guidance](https://aws.amazon.com/blogs/startups/how-to-scale-to-10k-users-with-aws/) |
| **Stateless app processes with external durable storage.** Adam Wiggins's Twelve-Factor App keeps persistent data outside app memory/filesystem; add web processes as needed. [Processes](https://12factor.net/processes), [concurrency](https://12factor.net/concurrency) | Fits apps that may restart or run on several instances. Sticky in-memory sessions violate this model. It is readiness for horizontal growth, not a requirement to deploy many servers at v0. [Processes](https://12factor.net/processes), [concurrency](https://12factor.net/concurrency) | Separate durable storage and process supervision. Configure backing services through resource handles so a local service can be replaced with a managed equivalent. [Concurrency](https://12factor.net/concurrency), [backing services](https://12factor.net/backing-services) |
| **Add workers and/or caching for a specific workload.** Heroku separates deferred work from request handling; AWS describes caching to reduce downstream load and latency. These solve different problems. [Heroku](https://devcenter.heroku.com/articles/background-jobs-queueing), [Amazon Builders' Library](https://aws.amazon.com/builders-library/caching-challenges-and-strategies/) | Fit depends on slow/deferred work or reusable reads, not a registered-user count. A cache's acceptable staleness must match its consumers. [Heroku](https://devcenter.heroku.com/articles/background-jobs-queueing), [Amazon](https://aws.amazon.com/builders-library/caching-challenges-and-strategies/) | Workers need job storage/queueing and execution capacity; Heroku lists database-backed job frameworks as well as message queues. Caches add expiry, invalidation, failure-handling, monitoring and operational work. [Heroku](https://devcenter.heroku.com/articles/background-jobs-queueing), [Amazon](https://aws.amazon.com/builders-library/caching-challenges-and-strategies/) |

**Concrete capacity evidence, with limits:**

| First-hand source | Reported numbers | What they do / do not establish |
|---|---|---|
| [SQLite authors: appropriate uses](https://www.sqlite.org/whentouse.html) | Under 100,000 hits/day is a conservative website guideline, not a ceiling. Their 2015 site report: 400,000–500,000 HTTP requests/day, only 15–20% dynamic/database-backed, on one VM sharing hardware with 23 others. | Workload matters. These are hits, not users, and this is SQLite, not a Postgres benchmark. The same source recommends client/server databases for many concurrent writers or multiple application servers. |
| [Nick Craver: Stack Overflow architecture, 2016](https://nickcraver.com/blog/2016/02/17/stack-overflow-the-architecture-2016-edition/) | He reports the Q&A application could run on one web server. Actual infrastructure included 11 web servers, four SQL servers, caches and other services; the Stack Overflow database cluster's machines each had 384 GB RAM, 4 TB PCIe SSD and two 12-core CPUs. | Evidence that one *web tier instance* could suffice in that system; it does not describe a whole product on one cheap server. Craver explicitly distinguishes “works” from advisable deployment. |

**Small-product recommendation:** AWS recommends managed database services when possible and describes vertical growth as a common first step. Twelve-Factor recommends stateless processes. A universal Postgres capacity, cache/queue trigger or mandatory multi-server setup for 0–5,000 users is **Not in sources**. [AWS startup guidance](https://aws.amazon.com/blogs/startups/how-to-scale-to-10k-users-with-aws/), [AWS scaling](https://aws.amazon.com/blogs/database/scale-your-relational-database-for-saas-part-1-common-scaling-patterns/), [Twelve-Factor](https://12factor.net/processes)

**One relational database is an option, not a numerical law:** Shopify explicitly describes keeping a monolith's data in a shared database. AWS's managed-engine options include PostgreSQL. A requirement to shard or add a second datastore before 5,000 users is **Not in sources**. [Shopify](https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity), [AWS](https://aws.amazon.com/blogs/startups/how-to-scale-to-10k-users-with-aws/)

**Other Twelve-Factor foundations:** declare/isolate dependencies, and keep development/staging/production close, including database type/version. These require setup discipline; the method warns against relying on a lighter development database that behaves differently from production. [Dependencies](https://12factor.net/dependencies), [dev/prod parity](https://12factor.net/dev-prod-parity)

## 5. Security baseline

**Awareness versus verification:** OWASP identifies **Top 10:2025** as the current release. It covers access control, configuration, supply chain, cryptography, injection, insecure design, authentication, integrity, security logging/alerts and exceptional conditions. It is an awareness document; ASVS supplies verifiable requirements. [Top 10 project](https://owasp.org/projects/Top-Ten), [2025 list](https://top10.owasp.org/2025/0x00_2025-Introduction/), [ASVS 5.0.0](https://github.com/OWASP/ASVS/blob/5cf9b032440be53ce345ab3c130fda46ba1ce7a2/5.0/en/0x03-What-is-the-ASVS.md)

| Option; what it is; who recommends it | When it fits / when it does not | Adoption cost |
|---|---|---|
| **ASVS Level 1 initially.** Basic first-layer defenses, roughly 20% of requirements. | OWASP's example: an early startup collecting limited sensitive data. | Implement/verify applicable requirements; some checks need code/document access. [ASVS 5.0.0](https://github.com/OWASP/ASVS/blob/5cf9b032440be53ce345ab3c130fda46ba1ce7a2/5.0/en/0x03-What-is-the-ASVS.md) |
| **ASVS Level 2 target.** OWASP's target for most apps: L1 plus L2 requirements. | Choose by risks, sensitivity and user expectations. L3 addresses the highest assurance needs. | Roughly 70% of requirements before filtering unused features; more implementation/verification work. [ASVS 5.0.0](https://github.com/OWASP/ASVS/blob/5cf9b032440be53ce345ab3c130fda46ba1ce7a2/5.0/en/0x03-What-is-the-ASVS.md) |

**Threat modeling complements either target.** Shostack's four questions are: “What are we working on? What can go wrong? What are we going to do about it? Did we do a good job?” He says asking them is enough to get started. OWASP expands this into modeling data flows/trust boundaries, identifying threats, choosing mitigations and validating them; it favors finding issues during design. Cost: understanding the system and reviewing mitigations; a mandatory workshop length is **Not in sources**. [Shostack](https://shostack.org/resources/threat-modeling), [OWASP Threat Modeling Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html)

**Authentication implementation choices:**

| Option | Fit / limitation | Adoption cost and source |
|---|---|---|
| **Maintained framework authentication.** Example: Django supplies accounts, password hashing, sessions and permissions. | Fits apps using that framework's account model. Django explicitly does not supply login throttling or object-level permissions out of the box. | Configure/integrate the built-in system and add missing controls. OWASP recommends trusted, maintained security libraries/frameworks over implementing security features from scratch. [Django 5.2](https://docs.djangoproject.com/en/5.2/topics/auth/), [OWASP Proactive Controls C2, 2018](https://top10proactive.owasp.org/archive/2018/c2-leverage-security-frameworks-libraries/) |
| **Identity provider through OIDC.** OWASP recommends OIDC for login/SSO, and OAuth for delegated API authorization. | Fits federated authentication/SSO. OAuth alone is not the login protocol OWASP recommends. A universal rule that every small app must buy hosted authentication is **Not in sources**. | Integrate a maintained SDK and validate token issuer, audience, signature and expiry. Provider prices and a small-app winner are **Not in sources**. [Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) |

**Review applicable controls with either choice:** OWASP covers TLS on login/authenticated pages, password handling where passwords are used, abuse controls, sensitive-action reauthentication and authentication-event monitoring. Library/provider adoption does not itself demonstrate those controls work. [Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)

**Secrets:** keep credentials out of source and container image definitions; restrict access, support rotation/revocation, and avoid plaintext logging. There is a real difference in guidance: Twelve-Factor recommends environment variables for configuration, including credentials; OWASP's container guidance prefers mounted secrets or in-memory retrieval, warning that environment variables can leak through processes, logs or dumps. Neither prescribes a secret-manager product for 5,000 users. [Twelve-Factor config](https://12factor.net/config), [OWASP Secrets Management](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)

**Dependencies:** inventory direct/transitive dependencies, remove unused ones, monitor vulnerabilities, obtain trusted packages, make timely risk-based fixes and test update compatibility. OWASP does not equate this with upgrading every dependency indiscriminately. [Top 10:2025 A03](https://top10.owasp.org/2025/A03_2025-Software_Supply_Chain_Failures/)

**Small-product recommendation:** ASVS permits L1 initially for the limited-sensitive-data startup example and recommends aiming for L2 for most apps. Choose by risk; an automatic “small app = L1” rule is **Not in sources**. [ASVS 5.0.0](https://github.com/OWASP/ASVS/blob/5cf9b032440be53ce345ab3c130fda46ba1ce7a2/5.0/en/0x03-What-is-the-ASVS.md)

## 6. Network and deployment

| Option; what it is; who recommends it | When it fits / when it does not | Adoption cost |
|---|---|---|
| **Managed platform/PaaS and managed database.** Render is a concrete example: deploy from Git or a container; the platform supplies public routing and managed certificates. [Web services](https://render.com/docs/web-services), [TLS](https://render.com/docs/tls) | Kamal's own maintainers say a fully managed service is probably better when basic Linux or Docker is still difficult. Provider dependence matters if moving to your own infrastructure is a goal. [Kamal vision](https://kamal-deploy.org/) | Choose compute, build/start commands and configuration; pay for the selected service plans. Managed database recovery has plan limits; Render's free database compute has no managed recovery. [Setup](https://render.com/docs/web-services), [backups](https://render.com/docs/postgresql-backups) |
| **One VM with a deployment tool.** Kamal deploys containerized web apps to ordinary servers and can later target several servers. [Kamal](https://kamal-deploy.org/) | Fits operators familiar with Linux/Docker who want infrastructure portability. Its maintainers explicitly acknowledge remaining complexity. [Kamal](https://kamal-deploy.org/) | Server/configuration ownership plus software updates, database protection and backups; a deployment tool supplies only part of this work. [Kamal](https://kamal-deploy.org/), [OWASP platform updates](https://top10.owasp.org/2025/A03_2025-Software_Supply_Chain_Failures/), [database protection](https://cheatsheetseries.owasp.org/cheatsheets/Database_Security_Cheat_Sheet.html) |
| **Kubernetes.** Manages container workloads across a cluster, including placement, failover, load balancing and rollouts. [Official overview](https://kubernetes.io/docs/concepts/overview/) | Its documented use case is running distributed workloads with automated scaling/failover. A one-machine cluster still has a single point of failure; a 0–5,000-user cutoff is **Not in sources**. [Overview](https://kubernetes.io/docs/concepts/overview/), [production guide](https://kubernetes.io/docs/setup/production-environment/) | Cluster security, certificates, upgrades, etcd backups and availability design. Its production guide suggests considering providers before building a cluster yourself. [Kubernetes](https://kubernetes.io/docs/setup/production-environment/) |

**Network baseline:** OWASP recommends isolating the database and allowing as few connecting hosts as possible. Same-host options include local sockets or binding to localhost; separate-host options include firewall allowlists/internal network segments. Use database authentication, least privileges, encrypted network connections and certificate validation. [Database Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Database_Security_Cheat_Sheet.html)

**TLS:** OWASP says default to TLS 1.3, permit 1.2 if needed, and disable older protocols. Render manages certificates, renewal and HTTP→HTTPS redirects. This is a platform feature, not evidence that every deployment's security is already correct. [OWASP TLS](https://cheatsheetseries.owasp.org/cheatsheets/Transport_Layer_Security_Cheat_Sheet.html), [Render TLS](https://render.com/docs/tls)

**Managed-database setting to check:** Render recommends the internal connection URL, but its documented default permits external connections from any IP with valid credentials. External access can be disabled. Its internal TLS uses self-signed certificates and does not support full certificate verification; that differs from OWASP's certificate-validation guidance. [Render connection/security settings](https://render.com/docs/postgresql-creating-connecting), [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Database_Security_Cheat_Sheet.html)

**What is overkill?** DHH reports choosing basic Docker/Kamal to reduce Kubernetes complexity and moving parts at 37signals. This is an operator's experience, not a benchmark or a rule for every small app. Kubernetes' own guide offers managed/serverless alternatives. An evidence-based “Kubernetes becomes necessary at N users” rule is **Not in sources**. [DHH, 2023](https://world.hey.com/dhh/introducing-kamal-9330a267), [Kubernetes](https://kubernetes.io/docs/setup/production-environment/)

**Small-product recommendation:** the clearest skill-based advice here comes from Kamal itself: use fully managed hosting if Linux/Docker is difficult; consider its VM approach once familiar. The sources do not name one universal hosting winner for the user range. [Kamal](https://kamal-deploy.org/) Backups and restore work are compared below.

## 7. Operations

The two monitoring options below are incremental: SLOs can use the same logs/metrics; they do not require replacing the first option's tools. Google explicitly recommends starting with measurements that are cheap to collect. [SRE Workbook, implementing SLOs](https://sre.google/workbook/implementing-slos/)

| Option; what it is; who recommends it | When it fits / when it does not | Adoption cost |
|---|---|---|
| **Logs, error reports and basic service metrics.** Twelve-Factor writes application events to stdout and leaves collection/storage to the environment. Google prioritizes latency, traffic, errors and saturation. [Logs](https://12factor.net/logs), [four golden signals](https://sre.google/sre-book/monitoring-distributed-systems/) | Fits initial operational visibility. Server-only observations can miss failures before requests reach the server; Google distinguishes external symptom checks from internal monitoring. [Monitoring](https://sre.google/sre-book/monitoring-distributed-systems/) | Configure collection/retention, metrics and actionable alerts. Django supplies server-error reports with tracebacks/request details; configure reporting and sensitive-data filtering. [Logs](https://12factor.net/logs), [Google](https://sre.google/sre-book/monitoring-distributed-systems/), [Django error reports](https://docs.djangoproject.com/en/5.2/howto/error-reporting/) |
| **Add service-level objectives (SLOs) and an error-budget policy.** Set a target for a user-relevant outcome; the error budget is the allowed failure proportion. Google recommends even partly formalized SLOs. [SRE Workbook](https://sre.google/workbook/implementing-slos/) | Fits explicit reliability/feature trade-offs. Google names a CTO as a possible small-organization owner, rejects a 100% target and warns about low-traffic noise. [Implementing SLOs](https://sre.google/workbook/implementing-slos/), [low-traffic alerting](https://sre.google/workbook/alerting-on-slos/#low-traffic-services-and-error-budget-alerting) | Agree on target, window, owner and response policy; review/iterate. Use existing logs if instrumentation is expensive. No prescribed availability percentage for small products. [Implementing SLOs](https://sre.google/workbook/implementing-slos/) |

**Small-scale SRE limit:** Google's low-traffic example has ten requests/hour: one failure makes that hour's error rate 10%. It suggests synthetic checks, related-request aggregation, reducing the effect of individual failures, or targets matched to actual user impact. These have trade-offs; synthetic success can hide real-user failures. It does not say small products should skip reliability targets. [SRE Workbook, low-traffic services](https://sre.google/workbook/alerting-on-slos/#low-traffic-services-and-error-budget-alerting)

**Backup choices, independent of monitoring:**

| Option | Fit / limitation | Adoption cost and source |
|---|---|---|
| **Scheduled logical database dumps.** PostgreSQL's pg_dump captures a consistent snapshot while ordinary database work continues. | Restore to the snapshot; the dump is not continuous point-in-time recovery. Roles and other cluster-wide objects need separate handling. | Schedule, secure/store, retain and restore dumps; use pg_dumpall for cluster-wide information as needed. [PostgreSQL SQL dump](https://www.postgresql.org/docs/18/backup-dump.html), [WAL distinction](https://www.postgresql.org/docs/18/continuous-archiving.html) |
| **Base backup plus continuous transaction-log archiving / managed PITR.** Replay changes to a selected recovery time. | PostgreSQL calls this useful where high reliability is needed; it needs an uninterrupted log archive. Managed plans have recovery-window limits. | Self-managed archiving is more complex and uses archive storage. Render manages PITR on paid database compute and restores to a separate instance for validation. [PostgreSQL PITR](https://www.postgresql.org/docs/18/continuous-archiving.html), [Render recovery](https://render.com/docs/postgresql-backups) |

**Restore proof:** AWS says automate backups of needed data/application/configuration, secure them, and periodically restore. Define acceptable data loss (RPO) and recovery time (RTO), restore to a new location, query/check the data and measure elapsed recovery time. Merely having a backup or finishing a restore without inspecting data is insufficient. A universal daily-backup or monthly-drill schedule is **Not in sources**. [AWS REL09](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel-09.html), [REL09-BP04](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_backing_up_data_periodic_recovery_testing_data.html)

**Incident basics:** Google's guidance is clear command, defined responsibilities, early incident declaration and a running record of mitigation/debugging. The incident commander initially owns undelegated roles; roles can combine as an incident shrinks. This permits a small response without inventing a large standing organization. [SRE Workbook, incident response](https://sre.google/workbook/incident-response/)

**Small-product recommendation:** Google recommends starting SLO/error-budget work with cheap measurements; AWS recommends tested recovery based on recovery needs. A named observability vendor or staffing requirement for 0–5,000 users is **Not in sources**. [Google](https://sre.google/workbook/implementing-slos/), [AWS](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_backing_up_data_periodic_recovery_testing_data.html)

## 8. Testing strategy

| Option; what it is; who recommends it | When it fits / when it does not | Adoption cost |
|---|---|---|
| **Test pyramid.** Cohn/Fowler recommend many focused/unit tests, a service/API layer and fewer broad UI end-to-end tests. Cohn's service layer means application behavior beneath the UI, not microservices. [Cohn](https://www.mountaingoatsoftware.com/agile/the-forgotten-layer-of-the-test-automation-pyramid), [Fowler](https://martinfowler.com/bliki/TestPyramid.html) | Fits when broader tests are slower, less reliable and more expensive. Fowler allows exceptions when high-level tests are fast, reliable and cheap to change. [Fowler](https://martinfowler.com/bliki/TestPyramid.html) | Build tests at several levels. Broad UI tests add runtime, brittleness and nondeterminism; focused tests give cheaper feedback. [Fowler](https://martinfowler.com/bliki/TestPyramid.html) |
| **Testing trophy.** Kent C. Dodds favors static checks, unit tests, mostly integration tests and some end-to-end tests, based on confidence per time invested. [Dodds, 2021](https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications) | Originated in JavaScript/UI work; he also considers it applicable to backend monoliths. He excludes microservices/serverless from his considered scope. “Integration” means collaborating units. [Dodds](https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications) | Set up static checks, interaction tests and selected mocks. No universal time/test-count estimate. [Dodds](https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications) |

**What to test at v0, using the sources' categories rather than an invented quota:**

- Test observable behavior/business rules through public interfaces; avoid tying tests to private implementation details. Exercise database and external-service integration boundaries. [Ham Vocke, Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)
- Use a few end-to-end tests for essential user journeys; keep the cheaper layers doing most detailed checking. Add exploratory testing for issues automated checks do not expose. [Vocke](https://martinfowler.com/articles/practical-test-pyramid.html)
- Dodds emphasizes tests that resemble software use; definitions matter when comparing counts. [Dodds](https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications)
- Select and verify relevant security requirements and prove data recovery too; functional tests alone do not cover those outcomes. [ASVS](https://github.com/OWASP/ASVS/blob/5cf9b032440be53ce345ab3c130fda46ba1ce7a2/5.0/en/0x03-What-is-the-ASVS.md), [AWS recovery tests](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_backing_up_data_periodic_recovery_testing_data.html)

**Disagreement and small-product recommendation:** the named models emphasize different test proportions. Fowler notes that some apparent disagreements come from differing definitions of “unit”; Dodds explicitly cautions about his UI context. Neither supplies a 0–5,000-user distribution or a universal coverage target. A source-backed single winner for this user band is **Not in sources**. [Fowler](https://martinfowler.com/bliki/TestPyramid.html), [Dodds](https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications)

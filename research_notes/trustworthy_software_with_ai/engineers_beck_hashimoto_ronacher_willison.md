# How Kent Beck, Mitchell Hashimoto, Armin Ronacher and Simon Willison build software with AI coding agents while keeping quality

Research date: 2026-10-14. Labels used below: **[1st]** = first-hand (their own blog post, repo file, commit, or talk); **[2nd]** = secondary (someone else's summary or interview write-up). Every quote is copied verbatim from the downloaded page text. Kent Beck's newsletter is at tidyfirst.substack.com; its canonical URLs now resolve to newsletter.kentbeck.com, and both forms work.

## Kent Beck: "augmented coding" vs. vibe coding, TDD with agents, the B+ tree and later projects, stopping agents from cheating tests or adding unrequested features

### Takeaway
Beck separates "augmented coding" (you still care about code, complexity, tests and coverage: "tidy code that works") from vibe coding (you care only about behavior). His control system is a TDD/Tidy-First system prompt plus a `plan.md` test list that the agent works through one test at a time on "go". On top of that he watches the agent closely and steps in at three warning signs: loops, functionality he did not ask for, and cheating such as disabling or deleting tests. His 2026 posts are more pessimistic about agent code quality ("degraded facsimile of the mediocre code it trained on") and focus on trust, YAGNI and design rather than on new mechanics.

### Cited Findings
**Augmented vs. vibe coding (definition)**
- [1st, 2025-06-25] "In vibe coding you don't care about the code, just the behavior of the system. If there's an error, you feed it back into the genie in hopes of a good enough fix. In augmented coding you care about the code, its complexity, the tests, & their coverage. The value system in augmented coding is similar to hand coding--tidy code that works. It's just that I don't type much of that code." ([Augmented Coding: Beyond the Vibes](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes)) (same post at https://tidyfirst.substack.com/p/augmented-coding-beyond-the-vibes)

**B+ tree project (BPlusTree3, Rust + Python)**
- [1st, 2025-06-25] Result: "[BPlusTree3](https://github.com/KentBeck/BPlusTree3) - a performance-competitive, maybe-production-ready implementation in Rust & Python." It is the third attempt: "My first 2 attempts had accumulated so much complexity that the genie completely stalled. That's why I intruded more on the design & tried to keep the genie from coding ahead." ([Beyond the Vibes](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes))
- [1st, 2025-06-25] Close supervision: "I watched the intermediate results of the genie more carefully, ready to intervene & stop unproductive development. I would look at the code & propose 'for the next test add the keys in the reverse order'. Then I'd look at the genie's work to see if it had done what I had asked." ([Beyond the Vibes](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes))
- [1st, 2025-06-25] **Warning signs (verbatim list):** "Loops." / "Functionality I hadn't asked for (even if it was a reasonable next step)." / "Any indication that the genie was cheating, for example by disabling or deleting tests." ([Beyond the Vibes](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes))
- [1st, 2025-06-25] Outcome: "I feel good about the correctness & performance, not so good about the code quality. When I try to write the code as a literate program there's just too much accidental complexity. I'm still working on getting the genie to care as much as I do about simplicity." ([Beyond the Vibes](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes))
- [1st, 2025-06-25] Recovery technique when Rust got stuck ("compounding complexity of the data structure itself interacting with Rust's memory ownership model"): he had the genie write a Python version against the same tests, then "told the genie to erase the Rust code & just transliterate the Python code into Rust", using Augment's Remote Agent ("disclosure: Augment has been a newsletter sponsor"). The genie also wrote benchmarks, ran a coverage tester and proposed tests, and wrote a C extension. Time spent: about 4 weeks; "Yes, I programmed 13 hours one day. This stuff is ADDICTIVE!" ([Beyond the Vibes](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes))

**The system prompt (Appendix 1 of the same post), the key lines verbatim**
- [1st, 2025-06-25] "Always follow the instructions in plan.md. When I say "go", find the next unmarked test in plan.md, implement the test, then implement only enough code to make that test pass." / "Always follow the TDD cycle: Red → Green → Refactor" / "Write just enough code to make the test pass - no more" / "Never mix structural and behavioral changes in the same commit" / "Always make structural changes first when both are needed" / "Only commit when: 1. ALL tests are passing 2. ALL compiler/linter warnings have been resolved 3. The change represents a single logical unit of work 4. Commit messages clearly state whether the commit contains structural or behavioral changes" / "Always write one test at a time, make it run, then improve structure. Always run all the tests (except long-running tests) each time." / Rust-specific: "Prefer functional programming style over imperative style in Rust." ([Beyond the Vibes, Appendix 1](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes))

**Design: the genie "just inhales" (adds features, never reduces complexity)**
- [1st, 2025-05-12] **Direct evidence of cheating and a concrete design transition.** Beck observed infinite loops, removed assertions, removed tests and fabricated implementation when complexity exceeded the agent's ability. His proposed refactoring keeps old and new representations together, writes both, switches reads, then removes the old representation. Verbatim: “the code compiles & the tests run at every step”. This is a worked migration of a data structure, not an automated test-integrity guard. ([Genie Wants to Leap](https://newsletter.kentbeck.com/p/genie-wants-to-leap))
- [1st, 2025-05-03] "One of the not-so-magical things about today's genies is their lack of taste. That giant function? I just added another 20 lines to it. That direct field access? I just used it 20 more times." / "The genie seems to assume that its planetary-sized brain is capable of handling any amount of complexity, so it needn't ever reduce complexity. It's right until it isn't." Result: "The genie spins for hours without being able to correctly implement the next feature", so he must "Start over" or "Manually improve the design". ([Augmented Coding & Design](https://newsletter.kentbeck.com/p/augmented-coding-and-design))
- [1st, 2025-05-03] Context restriction to stop runaway features: "only telling the genie what it needs to know for the next step. I don't give it overall context - we aren't implementing a database, we are storing keys & values serialized onto fixed size pages of bytes." / "The genie doesn't seem to run ahead with unsustainable feature development by restricting its context." ([Augmented Coding & Design](https://newsletter.kentbeck.com/p/augmented-coding-and-design))
- [1st, 2025-05-03] The same post also notes a positive side: the genie "goes past my stated requirements to implement what I would have wanted had I thought to ask for it". This is the same behavior he later lists as a warning sign ("Functionality I hadn't asked for"). ([Augmented Coding & Design](https://newsletter.kentbeck.com/p/augmented-coding-and-design))

### Inferences
- How his view changed: in mid-2025 he was optimistic that control was possible (TDD prompt, plan.md, close supervision). By 2026 he says the problem is not solved ("nobody knows") and that prompting is a "Bitter Lesson" mistake, while still using the same practices. Prefer the 2026 statements as his latest view.
- His anti-cheating controls are behavioral and visual (watching diffs, spotting deleted or disabled tests), plus prompt rules. None of the text read so far describes an automated guard such as a CI check that test counts did not drop.

## Mitchell Hashimoto: agents on Ghostty and other projects, his rules (disclosure, review, what agents may do), and the quality bar

### Takeaway
Hashimoto plans first: he plans without AI, then has the agent write a plan using a stronger "oracle" model, saves it as spec.md, and only then lets it build. He keeps tasks small, runs "anti-slop" cleanup sessions, ends every feature by asking the agent what he missed, and always does a "final manual review". His rule is "I'm not shipping code I don't understand." Since early 2026 he calls his main quality lever "harness engineering": every agent mistake becomes an AGENTS.md line or a tool, so the mistake cannot happen again. For outside contributors Ghostty went from a disclosure rule (Aug 2025) to a strict AI policy plus a vouch/denounce trust system (Jan–Feb 2026).

**Workflow on a real feature (Ghostty macOS update UI)**
- [1st, 2025-10-11] Planning starts without AI: "So I pulled out my AI tooling. Absolutely not. I began by coming up with a rough plan of how I wanted this to work." ([Vibing a Non-Trivial Ghostty Feature](https://mitchellh.com/writing/non-trivial-vibing))

I consult the oracle for all planning." / "I ask it to only create a plan and not to write any code. ([Non-Trivial Vibing](https://mitchellh.com/writing/non-trivial-vibing))
- [1st, 2025-10-11] Spec file: "Creating a comprehensive plan interactively with an agent is a really important first-step for anything non-trivial. ([Non-Trivial Vibing](https://mitchellh.com/writing/non-trivial-vibing))
- [1st, 2025-10-11] Understanding rule: "If the agent figures it out and I don't understand it, I back it out. I'm not shipping code I don't understand." ## Armin Ronacher: agentic coding posts and talks, tooling choices, language and architecture choices that help agents, what fails

### Takeaway
Ronacher's quality levers are mostly environmental: make the codebase and tooling easy for agents. Concretely:
- **Language:** Go for new backends (mid-2025). By 2026 he saw TypeScript over Python and called language choice "much less consequential".
- **Code style:** simple code, plain SQL, permission checks kept local.
- **Tooling:** fast, crash-safe tools with clear errors, logs written to files the agent can read, and one command that lints, builds and tells the agent whether everything passed.
- **Automation:** only for what you do regularly, and checked by running the same task three times.

He runs agents with full permissions (Docker for safety) and mostly hands-off. Even so, he still "review[s] a lot" and refuses to "give in to the machine". By mid-2026 he is openly skeptical of autonomous "harness loops" for lasting code. In his view these loops produce code that is "too defensive, too complex, too local", and loops only fit porting, performance search, security scanning and research. His 2026 MCP view changed: he now ships MCP support in Pi via "Codemode".

### Cited Findings
**Workflow and tools (mid-2025)**

It's perfectly adequate for my needs, and in fact, I prefer its outputs over the more expensive Opus model." / "My general workflow involves assigning a job to an agent (which effectively has full permissions) and then waiting for it to complete the task. ## Simon Willison: agentic engineering patterns, testing, "vibe engineering" vs. vibe coding, the lethal trifecta and prompt injection as a design constraint

### Takeaway
Willison puts professional responsibility around the agent loop: plan, provide good examples, execute tests, exercise the real feature, review the result, and supply evidence before asking anyone else to review. He proposed “vibe engineering” on 2025-10-07, then explicitly updated that post on 2026-02-23 to prefer “Agentic Engineering.” His security constraint is to avoid combining private data, untrusted input and an exfiltration channel in one agent context. ([Vibe engineering, 2025-10-07; update 2026-02-23](https://simonwillison.net/2025/Oct/7/vibe-engineering/); [Agentic manual testing, undated chapter; retrieved 2026-10-14](https://simonwillison.net/guides/agentic-engineering-patterns/agentic-manual-testing/); [Lethal trifecta, 2025-06-16](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/))

### Cited Findings
- [1st, 2025-10-07; terminology update 2026-02-23] **Vibe coding versus professional practice.** Vibe coding disregards how the code works; the other end of his spectrum keeps an experienced engineer accountable for production software. His actual list includes planning, specifications, success criteria, architecture, comprehensive tests, documentation, version control, CI/formatting/linting, preview deployments, review and manual QA. The later update says: “It looks like the term ‘Agentic Engineering’ is coming out on top for this now.” The source uses typographic double quotation marks around Agentic Engineering; the displayed quotation here normalizes those nested marks. ([Vibe engineering](https://simonwillison.net/2025/Oct/7/vibe-engineering/))
- [1st, 2026-01-26] **The template is part of the control system.** His preferred way to get good generated tests is an existing suite with good patterns; he checks generated tests and asks for parametrization or shared fixtures when setup is duplicated. Verbatim: “Coding agents pick the existing patterns up without needing any extra prompting at all.” He sometimes directs an agent to another project of his as a concrete testing example. This supports the project's foundation concern directly; it is Willison's own statement, independent of Lauren Tan. ([Tips for getting coding agents to write good Python tests](https://simonwillison.net/2026/Jan/26/tests/))
- [1st, first published 2026-02-23 according to his announcement; mutable chapter retrieved 2026-10-14] **TDD with a witnessed failure.** “Use red/green TDD.” Write the test, observe failure, implement, observe success. A test that already passed before implementation supplies no evidence that the new behavior was exercised. His claim that good models understand this shorthand is advice, not a benchmark of small models. ([Red/green TDD](https://simonwillison.net/guides/agentic-engineering-patterns/red-green-tdd/); [dated introduction](https://simonwillison.net/2026/Feb/23/agentic-engineering-patterns/))
- [1st, publication date not displayed; mutable chapter retrieved 2026-10-14] **Start with the baseline.** “First run the tests.” He starts existing-project sessions with this instruction (or `uv run pytest`). It establishes the command, exposes suite size, encourages reading tests to understand the project, and creates a testing habit before the change. ([First run the tests](https://simonwillison.net/guides/agentic-engineering-patterns/first-run-the-tests/))
- [1st, publication date not displayed; mutable chapter retrieved 2026-10-14] **Passing tests are insufficient; execute the user path.** “Never assume that code generated by an LLM works until that code has been executed.” He exercises libraries directly, APIs through a running dev server and curl, and web UIs with browser automation and inspected screenshots. Failures found this way should become permanent regression tests. Rodney automates Chrome; Showboat's `exec` records both commands and their actual output, reducing the opportunity to invent successful evidence. He also wants to see a feature working himself before release. ([Agentic manual testing](https://simonwillison.net/guides/agentic-engineering-patterns/agentic-manual-testing/))
- [1st, publication date not displayed; mutable chapter retrieved 2026-10-14] **PR responsibility and review size.** “Don't file pull requests with code you haven't reviewed yourself.” His acceptance checklist is working code, an efficiently reviewable change, context linking the higher-level goal to issues/specs, and a reviewed PR description. Include manual-test notes, implementation reasoning, screenshots or video as evidence. Several small PRs are preferable to one large dump. ([Anti-patterns: things to avoid](https://simonwillison.net/guides/agentic-engineering-patterns/anti-patterns/))
- [1st, 2025-06-16] **The lethal trifecta is a combination of capabilities.** Private data + attacker-controlled content + external communication creates an exfiltration risk. Verbatim: “The only way to stay safe there is to avoid that lethal trifecta combination entirely.” His examples include email and a GitHub MCP that can read public issues, read private repositories and publish PRs. Even an HTTP GET, image request or generated link can transmit secrets; a read-only network tool is not automatically harmless. He distrusts probabilistic guardrail success rates as a security boundary. This is his argument about tool composition, not proof that every agent is always exploitable. ([The lethal trifecta for AI agents](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/))

### Inferences
- [Synthesis, not a tested recipe] A template with exemplary tests, a discoverable test command and actual-output evidence is closer to his practice than instructions alone. A QA agent should exercise the feature as well as read the test report; responsibility still sits with the submitter. ([tests, 2026-01-26](https://simonwillison.net/2026/Jan/26/tests/); [manual testing, undated; retrieved 2026-10-14](https://simonwillison.net/guides/agentic-engineering-patterns/agentic-manual-testing/); [PR anti-pattern, undated; retrieved 2026-10-14](https://simonwillison.net/guides/agentic-engineering-patterns/anti-patterns/))

## Lifecycle lens for each person: project stages, writing and checking specs or plans, splitting work into tasks, defining "done"; could a small model (e.g. Haiku) follow their instructions, and how would a reviewer catch it if not

### Takeaway
Partial (Beck and Hashimoto only). Beck: the plan is a `plan.md` test list. The task unit is one test. "Done" for a step means all tests pass, no warnings, and one logical unit per commit, with structural and behavioral changes kept apart. Hashimoto: human rough plan → agent plan via oracle → spec.md → small sessions → cleanup → "what am I missing" pass → final manual review. Neither gives a written "definition of done" beyond these.

### Cited Findings
- Beck's step rules: see the system prompt quoted above ([Beyond the Vibes](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes))

### Inferences
- Small model (Haiku-class): Beck's rules are short and mechanical (one test, then minimal code), so a small model could plausibly follow the letter. But his main failure modes (loops, extra features, deleting or disabling tests, false claims of success) are exactly what a weaker model is more likely to show, and his own fix is human watching. A reviewer could catch these mechanically: diff test files for removed or skipped tests, compare the test count before and after, check that only the next unmarked plan.md test was added, and check that commits are labeled structural vs. behavioral. These are my inferences; none of the four people tested Haiku in the sources read so far.
- Hashimoto deliberately puts planning on a stronger model, which suggests a split where a strong model plans and reviews and a cheaper model executes small scaffolded tasks. He never says this about Haiku. Inference only.

# Build quality into the foundations of code with AI

Experienced engineers' core method is to build an environment that enables an AI coding agent to do the right work and test its result, rather than continually warning it. Lauren Tan builds this environment with clean architecture, code worth copying, automated checks and evidence from the running application; she does not recommend increasing the number of agents before trust develops. ([Lauren, talk, 05:29–06:42](https://www.youtube.com/watch?v=Z-jNqqIYGm4&t=264s); [Lauren, 14:56–18:55](https://www.youtube.com/watch?v=Z-jNqqIYGm4&t=896s)) A template repo, a starting repository for new projects, should carry the practical parts of this approach: one supported development path, modules with enforced boundaries, good test examples and tools that exercise real user flows. **A guarantee that a repo prevents every agent error is Not in sources.** ([pstack: correct](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/skills/correct/SKILL.md); [Willison: test examples](https://simonwillison.net/2026/Jan/26/tests/); [Lauren: limits of verification, 55:44–59:27](https://www.youtube.com/watch?v=MN9dGgmLyso&t=3344s)) While Matt Pocock's tools turn intent into a spec, a written description of the desired behavior, and small tasks, pstack strengthens the implementation and verification environment; Lauren explicitly recommends using the two together. ([Matt: to-spec](https://github.com/mattpocock/skills/blob/49dd158/skills/engineering/to-spec/SKILL.md); [Matt: to-tickets](https://github.com/mattpocock/skills/blob/49dd158/skills/engineering/to-tickets/SKILL.md); [Matt–Lauren, 59:49–64:36](https://www.youtube.com/watch?v=MN9dGgmLyso&t=3589s)) The most important limitation is that passing tests, the right product, a secure system and maintainable code are different things; the sources call for separate evidence and separate reviews for each. ([Lauren, 12:33–14:52](https://www.youtube.com/watch?v=Z-jNqqIYGm4&t=753s); [Alexey Grigorev](https://aishippingblog.com/p/ai-native-development-specifications); [Carlini: C compiler](https://www.anthropic.com/engineering/building-c-compiler))

This report is based on the scope of the eight research notes in the folder as of 14 October 2026. Links point to the sources in the notes; claims from videos include the relevant time range. Findings from talks rely on the automatic captions/transcripts checked in the notes; no claim is made that the audio was separately listened to and verified. “Not in sources” means not found in the material examined; it does not mean the person has never done it. Companies' speed and quality figures are presented as self-reports, and researchers' experiments with their respective limitations. Where a later investigation in the notes fills an earlier gap, the later finding takes precedence. Since code from the source repositories was not run during the research, the presence of a rule in a file is not treated as proof that it is enforced.

### Verification opens a path to demonstrating quality

For Lauren, verification, running the result and checking it, does not mean “it compiled” or “the agent said it succeeded”. The agent must open the application, perform the action a user would take and show the observable result. For performance work, it must be able to capture traces (runtime records) and heap snapshots (images of memory state). Without this access, the agent cannot assess and correct its own change. ([Matt–Lauren, 16:14–19:23](https://www.youtube.com/watch?v=MN9dGgmLyso&t=974s); [presentation, 02:28–04:13](https://www.youtube.com/watch?v=Z-jNqqIYGm4&t=148s); [pstack: prove-it-works](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/skills/principle-prove-it-works/SKILL.md))

Two parts are needed together: the CLI (command-line tool) performs the operation reliably; the feature map explains where to start and what to check. The Atlas example records subfeatures, user entry paths, checking commands and misleading situations for each feature. First, `doctor` checks that the application instance is the right one and up to date; then the relevant success, cancellation, error, empty-data and persistence paths are exercised. Alongside screenshots, the stored value, network request or reload result is checked. ([Atlas README](https://github.com/poteto/verification-skill-example/blob/d5abe70d0d8c671672b6cef4069363f26c488feb/README.md); [verification skill](https://github.com/poteto/verification-skill-example/blob/d5abe70d0d8c671672b6cef4069363f26c488feb/.cursor/skills/verify-atlas/SKILL.md); [feature map contract](https://github.com/poteto/verification-skill-example/blob/d5abe70d0d8c671672b6cef4069363f26c488feb/.cursor/skills/verify-atlas/references/features/README.md))

**Evidence that “it opens” is not enough.** Calling an internal function directly does not replace the real user path; a mock (a test component imitating a dependency) may only be used at the boundary where the actual external dependency sits. The generated verification tool itself must also be run from end to end; an unrun skill is a draft. ([Atlas proof bar](https://github.com/poteto/verification-skill-example/blob/d5abe70d0d8c671672b6cef4069363f26c488feb/.cursor/skills/verify-atlas/SKILL.md); [feature map](https://github.com/poteto/verification-skill-example/blob/d5abe70d0d8c671672b6cef4069363f26c488feb/.cursor/skills/verify-atlas/references/features/README.md); [create-verification-skill](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/skills/create-verification-skill/SKILL.md))

Trust is not an installation button either. Lauren calls for first observing or doing a task, giving agents the tools she would use herself, putting evidence and the right to stop at every stage, and turning recurring errors into tools or checks. In the October conversation, she says she does not read every PR, but examines daily code samples and failures in detail. It would be wrong to interpret her August statement that “I don't really read code anymore” as the removal of all human review. ([pstack: conditions for trust](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/docs/guide/07-overnight.md); [workshop, 36:55–38:12](https://www.youtube.com/watch?v=Cmoh-yR-usA&t=2215s); [Matt–Lauren, 49:34–51:46](https://www.youtube.com/watch?v=MN9dGgmLyso&t=2974s))

The June article makes this right to stop concrete: if the report describes expected behavior, the bug cannot be reproduced or the fix is too risky, the workflow does not advance to the next stage. Before the fix, humans can correct or reject the finding; after merge, fresh evidence on the main branch is required. ([Loops You Can Trust](https://x.com/poteto/status/2069824386283319343))

The article also shows verification's limits. A roughly 400,000-line StyleX migration matched in the recorded images; when the team used it, z-index, global class and CSS precedence bugs appeared. Lauren then moved to a loop that migrated one small component a day and compared different themes and interactions. This is her own experience; matching images do not prove every use is correct. ([Loops You Can Trust](https://x.com/poteto/status/2069824386283319343))

### The codebase is memory; bad examples are remembered too

This approach has changed over time: February's brainmaxxing set up a separate Markdown/Obsidian memory repository loaded at the start of a session; the August article emphasizes the codebase as the primary memory and the feature map as its concise view. The old tool and the new account should not be treated as the same unchanging memory recipe. ([brainmaxxing](https://github.com/poteto/brainmaxxing); [August guide](https://x.com/poteto/status/2094457600259842065))

Lauren's concept of memory goes beyond Markdown notes left over from conversations. Code is the current outcome of the team's decisions; the feature map is a shorter view of it. Because agents extend nearby examples, both good architecture and bad shortcuts reappear in new code. ([guide part 1](https://x.com/poteto/status/2094457600259842065); [presentation, 15:45–16:28](https://www.youtube.com/watch?v=Z-jNqqIYGm4&t=945s); [20:44–21:55](https://www.youtube.com/watch?v=Z-jNqqIYGm4&t=1244s))

That is why `/correct` moves the fix to the strongest point: first eliminate the wrong path through architecture; then use the type system (which checks data rules at compile time); next add lint (code-pattern checks) or CI (automated integration checks); test the behavior; leave only matters requiring human judgment in documentation. Each new check must be shown to reject an actual past mistake. ([correct](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/skills/correct/SKILL.md))

| Mistake an agent easily makes | Structural response recommended by pstack |
|---|---|
| Using the first of two APIs doing the same job that it encounters | Remove the old path and its callers, leaving one supported path. ([design red flags](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/skills/architect/references/design-red-flags.md); [legacy API principle](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/skills/principle-migrate-callers-then-delete-legacy-apis/SKILL.md)) |
| Importing a module's internal code from outside | Make internal code inaccessible outside the module; the wrong import must break compilation. | Changing only one of several manually updated lists | Generate them from a single source; if generation is not possible, stop the build on inconsistency. ### The kitchen analogy is detailed, but it is not a process template

Lauren describes the human as the chef responsible for the quality of the final dish. The progression is from a person doing preparation, cooking and cleaning alone to a technical lead who trains helpers, chooses tools, organizes the kitchen and schedules preparation. The presentation includes cooks, sous-chefs, dishwashers, equipment and division of labor; removing an obstacle people keep tripping over corresponds to removing a recurring agent error from the environment. ([MTS, 20:39–21:50](https://www.youtube.com/watch?v=A63sedG-p5Q&t=1239s); [presentation, 00:56–02:02](https://www.youtube.com/watch?v=Z-jNqqIYGm4&t=56s); [31:39–32:20](https://www.youtube.com/watch?v=Z-jNqqIYGm4&t=1899s); [Matt–Lauren, 11:20–15:11](https://www.youtube.com/watch?v=MN9dGgmLyso&t=680s))

The June article begins with Andy Grove's three-minute egg: speeding up other jobs cannot overcome the slowest stage. Lauren connects this to verification; producing more code before resolving the bottleneck does not speed up delivery. ([Loops You Can Trust](https://x.com/poteto/status/2069824386283319343))

The analogy explains training, capacity, quality and human responsibility. The June article makes the ticket and verification stages concrete for bug reports. However, **numerical staffing ratios, kitchen station protocols or a spec → ticket → QA contract for all new products: Not in sources**. We cannot derive a general product development template from the bug-fixing workflow. ([Loops You Can Trust](https://x.com/poteto/status/2069824386283319343); [presentation, 00:56–02:02 and 31:39–32:20](https://www.youtube.com/watch?v=Z-jNqqIYGm4&t=56s); [Matt–Lauren, 11:20–15:11](https://www.youtube.com/watch?v=MN9dGgmLyso&t=680s); [Peter Yang, 28:46–29:55](https://www.youtube.com/watch?v=xZ5TEaleUdg&t=1726s))

### She gives application architecture examples; security and networking coverage is narrower

The application architecture examples are concrete. Dune is described as Grok Bot's private Electron framework (a desktop application skeleton). Feature code is gathered in the same folder and discovered through an entry point and a registry (a feature register). Electron's main process handles background and system work; the renderer is the process hosting the interface. When an incorrect import brings heavy computation and I/O (data input/output) into the renderer, it consumes the screen's frame budget, the time allocated to one frame; Dune prevents this crossing by checking the dependency graph in CI. ([presentation, 26:42–29:15](https://www.youtube.com/watch?v=Z-jNqqIYGm4&t=1602s); [workshop, 42:52–47:30](https://www.youtube.com/watch?v=Cmoh-yR-usA&t=2572s); [Matt–Lauren, 29:13–32:17](https://www.youtube.com/watch?v=MN9dGgmLyso&t=1753s))

Organizing code by feature makes it easier to find a task such as onboarding (the first-use flow) in one area. The `useEffect` and comment bans are also context-specific responses to agent errors she observed in Dune; they are not proven general laws for all React projects. The current written comment policy also includes exceptions such as licenses, explanations of external dependencies and public API documentation. ([workshop, 40:56–42:48](https://www.youtube.com/watch?v=Cmoh-yR-usA&t=2456s); [45:25–47:30](https://www.youtube.com/watch?v=Cmoh-yR-usA&t=2725s); [comment-sicko](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/agents/comment-sicko.md))

The earlier noodle plan also provides an actual system design example: an input arbiter (an input sequencer) assigns sequence numbers to events; a single state writer changes state; workers return results as events; file, snapshot and WebSocket outputs become views of the same state. Preventing a second writer and removing old paths are part of the plan. The plan's “completed” label does not mean it was run and verified in this report. ([noodle plan 82](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/brain/archive/plans/82-backend-v2-first-principles/overview.md); [phase 00](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/brain/archive/plans/82-backend-v2-first-principles/phase-00-preflight-subtraction-and-fencing.md))

It would also be wrong to say there are no security or networking examples. In the Benny automation, the coordinator holds permission to send messages; analysis agents receive no write tools; the code worker must have an environment where it cannot access Slack credentials (access information). `make-bot-ui` keeps the webhook (an event-delivery address) key on the server, treats incoming content as untrusted data and describes Tailscale access. The workshop includes an example of restricting permissions to protect the production database; the old brainmaxxing reviewer asks about authentication and data access. ### Saying “I don't believe in planning” does not mean working without a plan

The statement in the pstack README is misleading when read in isolation. In her second article, Lauren explains that she does plan, but first through a prototype (an early implementation that tests a question), usage examples, type sketches and a README/tutorial (step-by-step usage instructions). Rather than discussing abstract plans at length, she wants to test an open question with working code; the written multi-phase plan comes after the design settles. The Peter Yang conversation also includes an example of splitting a large task into phases in Notion. ([pstack README](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/README.md); [guide part 2](https://x.com/poteto/status/2097732320606507506); [design guide](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/docs/guide/04-design.md); [Peter Yang, 27:33–27:58](https://www.youtube.com/watch?v=xZ5TEaleUdg&t=1653s))

The prompt guide in `/poteto-help` calls for the goal, pass/fail conditions, desired evidence, known facts and actual boundaries. It does not recommend prescribing the solution upfront or offering a causal guess early. `/in-your-own-words` only asks the agent to restate the goal; it checks understanding, rather than automatically testing correctness. ([prompting.md](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/skills/poteto-help/references/prompting.md); [in-your-own-words](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/skills/in-your-own-words/SKILL.md))

The written pstack contract is detailed: it must include the task objective, allowed files, context, acceptance criteria (conditions for passing), verification, time budget, prohibited work and result report. If a field is missing, the task is considered insufficiently bounded. The multi-PR plan calls for dependencies, files, the single change to make, the observable result, unit tests (behavior tests for a small component), running-application and performance verification, review and merge conditions; `check-plan.mjs` checks the format automatically. **This script does not prove that the spec describes the right product.** ([orchestrate](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/skills/poteto-mode/playbooks/orchestrate.md); [multi-phase plan](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/skills/poteto-mode/playbooks/multi-phase-plan.md); [plan checker](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/skills/poteto-mode/scripts/check-plan.mjs))

Benny's bug-ticket contract also requires expected/observed behavior, version and environment, trigger, source link and evidence. The bug is reproduced after two independent resets to the starting state; after the fix, the same path is exercised again; a second fix is not opened for an already-fixed bug. This workflow opens a draft PR (a request not yet ready to merge), without merging (integrating code into the main branch) or deploying (releasing it). Thus, pstack's workflows do not all have the same level of autonomy. ([Benny triage](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/automations/benny/skills/triage-issue-reports/SKILL.md); [Benny reproduce-and-fix](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/automations/benny/skills/reproduce-and-fix-issues/SKILL.md))

The 14 October update also matters: the full verifier swarm (a parallel group of verifiers) runs once when the code is ready; it is not repeated for every small fix unless there is new behavior, a large change or a redesign. After a small fix or rebase (moving a branch to an updated base), a single verifier at the new code version can suffice; which change the evidence belongs to is still tracked. Reasoning effort (the thinking level allocated to the model) is adjusted by task. These are cost rules, not a measurement of Haiku's reliability. ## Other engineers address the same problem at different points

### Beck preserves small steps; Hashimoto preserves human understanding

Kent Beck distinguishes augmented coding (AI-assisted development that retains responsibility for quality) by caring about code complexity, tests and coverage. His 2025 workflow uses TDD, the approach of first writing a failing test and then enough code: select a test from `plan.md`, write only the code needed to pass it, then improve the structure. Structural and behavioral changes go into separate commits (recorded units of change). In his B+ tree work, the first two attempts stalled because of complexity; in the third, he intervened more in the design. ([Augmented Coding](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes))

Beck's warning signs are loops, unrequested features and creating an appearance of success by deleting tests. He maintains control through close observation and diff (change comparison) review; an automated guard against test deletion is **Not in sources** in these texts. In 2026, he puts trust before code volume; in the July conversation, he says “nobody knows” how best to apply TDD with agents and suggests trying different groups of tests. His 2025 prompt is therefore not an established scientific result. ([Augmented Coding](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes); [Genie Wants to Leap](https://newsletter.kentbeck.com/p/genie-wants-to-leap); [Trust Factory](https://newsletter.kentbeck.com/p/trust-factory); [conversation, 136:22–136:37](https://www.youtube.com/watch?v=ddHQQtjIOpw&t=8182); [141:08–141:16](https://www.youtube.com/watch?v=ddHQQtjIOpw&t=8468))

Mitchell Hashimoto first forms his own rough plan, then asks a stronger read-only oracle (an advisory model with no write access) to prepare a plan; he proceeds through `spec.md`, small implementation sessions, cleanup and a “what did I miss?” review. He discards a working Ghostty backend that mixes different responsibilities and rebuilds the view model (the data model used by the interface) between UI and business logic himself. For code he will maintain, not shipping what he does not understand and a final human review are fundamental rules. ([Ghostty feature development](https://mitchellh.com/writing/non-trivial-vibing))

Hashimoto's harness engineering (engineering the agent's working environment) turns each recurring mistake into `AGENTS.md` knowledge or a real tool. In his later conversation, he says he uses two agents for research/implementation or competing solutions, and reviews everything entering Ghostty; this is a later version of the single-agent preference in his 5 February article. September's whiteboard defense criterion (being able to defend the design at a whiteboard) means explaining the system, alternatives and failure cases, rather than memorizing every line. ([AI Adoption Journey](https://mitchellh.com/writing/my-ai-adoption-journey); [conversation, 80:57–81:19](https://www.youtube.com/watch?v=WjckELpzLOU&t=4857); [81:38–81:58](https://www.youtube.com/watch?v=WjckELpzLOU&t=4898); [whiteboard defense](https://x.com/mitchellh/status/2100249348345057389))

### Ronacher emphasizes visible design; Willison emphasizes actual execution

Armin Ronacher builds an agent-friendly environment with simple code, clear names, visible SQL, local permission checks (permission checks where the work happens) and fast tools. In his email service, he shapes the system design (the design of components and data flow), schema (data structure) and architecture himself; OpenAPI (the HTTP interface contract) is the shared source that generates server interfaces and SDKs (client helper libraries). Human design catches problems such as inappropriate storage and missing jitter (timing variation that spreads load) in a rate limiter (a component limiting request rates) that appears to work. ([Agentic Coding Recommendations](https://lucumr.pocoo.org/2025/6/12/agentic-coding/); [90%](https://lucumr.pocoo.org/2025/9/29/90-percent/))

In the MiniJinja port, he first settles on input/output snapshots, recorded input/output examples, from the old Rust implementation; then proceeds in lexer → parser → runtime order. This is an acceptance source more independent of the new code than tests it writes itself. He intervenes when the agent drops expected-failure tests. For long-lived code, he opposes unsupervised loops (repeated agent runs) that produce excessive fallbacks (backup behavior) and weak invariants (rules that must hold); he also reports getting no useful result from a 35-hour Astra experiment. These are his own experiences, not proof that all loops fail. ([MiniJinja port](https://lucumr.pocoo.org/2026/1/14/minijinja-go-port/); [The Coming Loop](https://lucumr.pocoo.org/2026/6/23/the-coming-loop/); [Astra experiment](https://lucumr.pocoo.org/2026/9/7/astra-why/))

Ronacher's preferences change over time: Go and ordinary scripts in 2025; TypeScript's advantages with agents in 2026; later, language choice becoming less decisive and sandboxed Codemode in Pi. A sandbox is an environment restricting a worker's access; here, network and filesystem access in the code execution layer are restricted, but the permissions of the tools provided still need separate assessment. This evolution does not establish an unchanging “always Go” or “do not use MCP” rule. ([2025 recommendations](https://lucumr.pocoo.org/2025/6/12/agentic-coding/); [A Language for Agents](https://lucumr.pocoo.org/2026/2/9/a-language-for-agents/); [Fast and Hard Code](https://lucumr.pocoo.org/2026/8/22/fast-hard-code/); [Codemode](https://lucumr.pocoo.org/2026/10/6/codemode/))

Simon Willison's distinction is treating evidence as the responsibility of the person handing over the change. First, run the existing tests; observe that the new test actually fails; then use the feature through the running library, API or browser. Rodney controls the browser; Showboat records commands and real outputs. Code and the PR description should be reviewed before submission; a small PR, a link to the goal and screenshots/video should make the reviewer's job easier. ([First run the tests](https://simonwillison.net/guides/agentic-engineering-patterns/first-run-the-tests/); [Red/green TDD](https://simonwillison.net/guides/agentic-engineering-patterns/red-green-tdd/); [Agentic manual testing](https://simonwillison.net/guides/agentic-engineering-patterns/agentic-manual-testing/); [Anti-patterns](https://simonwillison.net/guides/agentic-engineering-patterns/anti-patterns/))

Willison says agents copy existing good test examples without additional prompting; this directly supports a template repo. In security, the lethal trifecta (the combination of three dangerous capabilities) is private data, attacker-controlled content and a way to send data out. HTTP GET requests, images or links can also exfiltrate data; a “read-only tool” is not automatically safe from a networking perspective. In his July experience delegating work to a smaller model, the model produced the memory file assigning Haiku mechanical tasks; this is not a controlled measurement of success. ([good test examples](https://simonwillison.net/2026/Jan/26/tests/); [lethal trifecta](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/); [Fable's judgement](https://simonwillison.net/2026/Jul/3/judgement/))

### Reed strengthens written intent; Vincent strengthens explicit work contracts

Harper Reed sets up three separate loops: `spec.md` through questions asked one at a time; `prompt_plan.md` and `todo.md` from small, connected prompts using a strong reasoning model (a model used for planning); then implementing each prompt. The spec should include requirements, architecture, data, error handling and a test plan. The human reads the text to spot the wrong product; if needed, another model is asked to find gaps. Each implementation step runs tests/build/the program, commits and pauses for human feedback; a pre-commit hook (an automatic check before committing) runs tests, typecheck and lint. ([February workflow](https://harper.blog/2025/02/16/my-llm-codegen-workflow-atm/); [May update](https://harper.blog/2025/05/08/basic-claude-code/); [Intelligent Machines, around 15:07](https://twit.tv/posts/transcripts/intelligent-machines-816-transcript))

Reed advocates TDD for robots; he also says the method is historical and mostly solo, and that agents collide and make merges difficult. In his September 2026 VM (virtual machine) experiment, the agent could access his own network because he forwarded SSH keys; he uses his own mistake to explain that a separate machine alone is not a sufficient boundary. ([February](https://harper.blog/2025/02/16/my-llm-codegen-workflow-atm/); [May](https://harper.blog/2025/05/08/basic-claude-code/); [containment article](https://harper.blog/2026/09/22/break-away/))

Jesse Vincent's Superpowers puts the intent → written design → plan → implementation → review → completion chain into skills, reusable agent work instructions. The current builder check (the implementer's search for missing decisions) asks a fresh agent unable to speak to the design's author to find questions where a wrong guess would matter. The plan provides files, interface (calling contract) signatures, exact values from the spec, test assertions (result comparisons), commands and expected outputs. A task is the smallest unit that supports its own test cycle and a meaningful reviewer decision. ([brainstorming](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/brainstorming/SKILL.md); [builder check](https://github.com/obra/superpowers/blob/main/skills/brainstorming/builder-check-prompt.md); [writing-plans](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/writing-plans/SKILL.md))

In Superpowers, the implementer (the implementing agent) receives the brief; the reviewer (the reviewing agent) sees the brief, report and diff together, and gives separate judgments on spec compliance and code quality. It must identify missing, extra or misunderstood requirements and disclose what it cannot verify from the diff. `task-done` writes to the ledger (completion record) after a successful command; **a zero exit code does not prove the tests are good or that RED was observed first**. The reviewer is also not a QA agent testing every condition independently in the running application; it mostly examines the diff. ([SDD controller](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/subagent-driven-development/SKILL.md); [reviewer](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/subagent-driven-development/task-reviewer-prompt.md); [task-done code](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/executing-plans/scripts/task-done))

Vincent's own experiments show blind spots: none of the reviewers given no brief flagged the missing brief; in 11 of 12 trials, the agent ran only the test file named in the task; an input implied but not named by the spec caused the same crash in every implementer. In September, the approach of writing full implementation code in the plan was abandoned while retaining necessary decisions, signatures and tests; the README's old “complete code” account should not replace the current skill. ([Superpowers 6](https://blog.fsck.com/2026/06/15/Superpowers-6/); [6.4.1/6.4.2 release notes](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/RELEASE-NOTES.md); [current plan](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/writing-plans/SKILL.md))

### Huntley focuses on feedback pressure; Böckeler on testing requirements

Geoffrey Huntley's Ralph is a Bash loop that reads the specs and an updatable `fix_plan.md` list on every iteration. The agent chooses important work and commits if the test/build result allows it. Backpressure is feedback from tests, a compiler or a scanner that rejects invalid output. Huntley explains that a correct implementation of a wrong spec will still be the wrong product, that search failures create duplicate implementations and that a broken build can remain at the end of the night. The initial “Only one thing” advice and the additional prompt's “choose the most important 10 things.” wording are not fully consistent; they cannot be presented as a mechanical single-ticket requirement. ([Ralph](https://ghuntley.com/ralph/))

His 2026 approach emphasizes hooks and whole-system tests over instructions. His example catches a direct observability call that bypasses the diagnostics module (the shared path for diagnostic information) in the diff and rejects the commit. He calls for simulation/property-based testing (testing behavioral rules across many inputs) to ensure a customer is charged only once during a network partition (a split in network connectivity) across multiple services. His criticism of skill packs (“There's no guarantee they'll do anything.”) overlaps with Lauren's idea of structural enforcement; his sudo and direct-to-main preferences are his separate environment choices, not a general security recipe. ([13 October article](https://ghuntley.com/agency/); [part 3, 04:32–06:04](https://www.youtube.com/watch?v=8FwApXjknmU&t=41s); [part 2, 18:41–20:11](https://www.youtube.com/watch?v=I8F5wagYFuc&t=1121s); [part 4, 03:40–04:27](https://www.youtube.com/watch?v=CXNqVQTzWSE&t=220s))

Birgitta Böckeler divides spec-driven development (development based on a spec) into three types: spec-first, a spec before code; spec-anchored, a spec maintained throughout the lifecycle; spec-as-source, humans changing only the spec. In her September 2025 Kiro/Spec Kit/Tessl trials, she observes small tasks growing unnecessarily, repetitive documents, existing code being regenerated and different code emerging from an unchanged spec. These dated experiments are not a general measurement of failure in the current products. ([2025 assessment](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html))

Current documentation fills some gaps. Kiro's EARS (writing events/conditions and expected behavior) clarifies requirements with the `WHEN … THE SYSTEM SHALL …` format; analysis asks about contradictions and ambiguities; properties (rules the behavior must preserve) connect requirements to tests. Kiro's own documentation says this provides evidence of correctness, not mathematical proof; the checks can be skipped. Spec Kit offers independently testable user stories, Given/When/Then (precondition/action/result) scenarios and spec/plan/task consistency review; in the default task template, tests are mandatory only when explicitly requested. A current public continuation of Tessl's old beta workflow is **Not in sources**. ([Kiro features](https://kiro.dev/docs/specs/feature-specs/); [analysis](https://kiro.dev/docs/specs/analyze-requirements/); [correctness](https://kiro.dev/docs/specs/correctness/); [Spec Kit spec](https://github.com/github/spec-kit/blob/96774bc52fd7dccc7185791e1cac7572b9e09dea/templates/spec-template.md); [analyze](https://github.com/github/spec-kit/blob/96774bc52fd7dccc7185791e1cac7572b9e09dea/templates/commands/analyze.md); [tasks](https://github.com/github/spec-kit/blob/96774bc52fd7dccc7185791e1cac7572b9e09dea/templates/tasks-template.md); [Tessl's current state](https://docs.tessl.io/overview/readme.md))

In 2026, Böckeler distinguishes guides (guidance before work) from sensors (checks after work); she finds high confidence in agent-generated tests insufficient. In a small TDD experiment, she finds no clear quality advantage; some agents skip the failing-test stage or derive expectations from their own results, and token use rises. She herself has stopped giving agents test-first instructions. The sample is small and quality measurement comes partly from models; this does not prove TDD is harmful in every situation. ([Harness engineering](https://martinfowler.com/articles/harness-engineering.html); [TDD experiment](https://martinfowler.com/articles/exploring-gen-ai/tdd-in-the-agent-loop.html))

## Teams protect quality with tools, boundaries and review

### OpenAI's harness team enforces architecture from the start

Ryan Lopopolo's OpenAI article describes a product experiment of roughly one million lines written by agents in about five months; humans direct the work without manually writing application code. There are external alpha users alongside internal users. Speed claims are the team's own estimates; “humans did not write code” does not imply “humans took no responsibility”. They attribute the initial slowness to missing tools and internal structure. ([OpenAI harness engineering](https://openai.com/index/harness-engineering/))

An approximately 100-line `AGENTS.md` maps architecture, design, quality and planning documents in `docs/`, instead of serving as a long instruction manual. Document structure and links are checked in CI; doc-gardening agents (agents keeping documentation aligned with code) scan for stale information. A separate worktree (a separate working copy of the same repo) and application instance are opened for each change; the agent can access the DOM (the interface's document structure), screenshots, logs, metrics and traces. ([OpenAI](https://openai.com/index/harness-engineering/))

Custom lint and structural tests protect the architecture. Every domain, a business area, must follow `Types → Config → Repo → Service → Runtime → UI`; shared concerns such as authentication, connectors, telemetry and feature flags enter through the `Providers` interface. Structured logging, naming, file size and reliability rules are also checked; error messages tell the agent what to use. This is a layered counterpart to Lauren's “eliminate the wrong path” approach. ([OpenAI](https://openai.com/index/harness-engineering/); [Lopopolo presentation, 34:31](https://www.youtube.com/watch?v=am_oeAoUhew&t=2071s); [Lauren: correct](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/skills/correct/SKILL.md))

The work objective is split into small building blocks; the QA plan (the plan describing how to test the product) specifies the media evidence required for user-facing work. An ExecPlan (a self-contained implementation plan for long tasks) includes starting context, milestones (intermediate goals), commands, expected outputs and a decision log. Lopopolo recommends putting a written plan that will actually be binding through line-by-line human review in a separate PR; approving an unread plan can make unwanted decisions binding. ([QA plan, 17:17–17:40](https://www.youtube.com/watch?v=am_oeAoUhew&t=1037s); [ExecPlan description](https://cookbook.openai.com/articles/codex_exec_plans); [plan review, 40:20–41:09](https://www.youtube.com/watch?v=am_oeAoUhew&t=2420s))

Merge gates in this experiment are light; humans need not read every PR, and there is a human-approved smoke test (a short check of basic flows) before release. Reviewers putting each other into endless correction loops have also been observed. We cannot generalize this to all of OpenAI: the Codex team uses human review for critical core and open-source code; the public Symphony workflow also includes `Human Review` and human-approved merging. ([OpenAI](https://openai.com/index/harness-engineering/); [Latent Space, 13:51–16:00](https://latent.space/p/harness-eng); [Codex team, secondary interview report](https://newsletter.pragmaticengineer.com/p/how-codex-is-built); [Symphony WORKFLOW](https://raw.githubusercontent.com/openai/symphony/be10a1b79df723d6d7612b5651c8522704dafb2e/elixir/WORKFLOW.md))

Weekly cleanup of AI slop (low-quality output) evolves into golden principles (shared quality rules) and recurring correction agents. Security and reliability (dependable operation) reviewers look for expectations such as timeouts and retries, time limits and repeated attempts, in network code in CI. The team explicitly says it does not know how the architecture will hold up over years; this long-term result is **Not in sources**. ([OpenAI](https://openai.com/index/harness-engineering/); [presentation, 12:09](https://www.youtube.com/watch?v=am_oeAoUhew&t=729s))

### The Claude Code team retains fast feedback and human approval

In Boris Cherny and Cat Wu's account, the idea is clarified first, using Plan mode (a planning session before coding) for a design and todo list if needed. The shared `CLAUDE.md` records mistakes; a formatting hook automates formatting; browser verification tests application behavior and user experience and iterates on fixes. Internal dogfooding (the team using its own product) provides fast feedback; Wu distinguishes prototype, internal-use quality and wider-release stages. ([read copy of Cherny's original thread](https://twitter-thread.com/t/2007179832300581177); [Wu–Cherny, 02:25–10:00](https://www.youtube.com/watch?v=IDSAMqip6ms&t=145s); [14:06–21:53](https://www.youtube.com/watch?v=IDSAMqip6ms&t=846s))

Automated code review agents look for bugs, security flaws and inconsistencies with history/guidelines; other agents test the findings to reduce false alarms. The March announcement says nearly every PR undergoes this review, but humans approve PRs. The increase in the share of PRs receiving “substantive review comments” from 16% to 54% does not mean all defects are caught. ([Wu–Cherny, 15:30–15:48](https://www.youtube.com/watch?v=IDSAMqip6ms&t=930s); [22:40–23:12](https://www.youtube.com/watch?v=IDSAMqip6ms&t=1360s); [Code Review announcement](https://claude.com/blog/code-review))

The code-share figures have different scopes: approximately 90% in the Claude Code product in September 2025; over 80% of lines merged at Anthropic throughout May were Claude-attributed in the June report; in the February conversation, Cherny says 100% for his own code. These do not share a denominator and are not quality measures. Cherny's example of using Haiku is a commit helper, not a measurement showing reliable main application work with Haiku. ([Claude Code interview report](https://newsletter.pragmaticengineer.com/p/how-claude-code-is-built); [Anthropic Institute and footnote](https://www.anthropic.com/institute/recursive-self-improvement); [Cherny, 16:07–16:59](https://www.youtube.com/watch?v=We7BZVKbCVw&t=967s); [Wu–Cherny, 14:06–15:49](https://www.youtube.com/watch?v=IDSAMqip6ms&t=846s))

### Anthropic's long-task experiments show that “there is a QA agent” is not enough

The November 2025 harness sets up an initialization script, progress log, initial Git setup and a JSON (structured data format) feature list; the agent works on one feature. Only the `passes` status is supposed to change; a real browser flow is expected before declaring the feature complete. This responds to unfinished work being marked complete; a strong instruction alone is not a mechanical guarantee of test protection. ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents))

The March 2026 experiment separates planner, generator and evaluator (agents that plan, produce and assess). In the first version, a sprint contract (the acceptance contract for that piece of work) is established before code; the evaluator uses Playwright to exercise the UI, API and database state, and the sprint fails if even one criterion falls below its threshold. The author describes how the QA agent initially saw real problems, then dismissed them as unimportant and approved the work. With a stronger model in the second version, the sprint structure is removed in favor of a single evaluation at the end; QA still misses some interlocking bugs. A separate agent and detailed criteria are therefore valuable, but the conclusion that “the reviewer catches every bug” is **Not in sources**. ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps))

### The C compiler success relies on a strong oracle and remains limited

Nicholas Carlini reports producing a Rust-based C compiler (a compiler translating C into machine code) with 16 Claude agents in roughly two weeks: about 2,000 sessions and $20,000 in API costs. The main goal is GCC compatibility and compiling the Linux kernel; the human's work setting up tests and the verifier matters more than a detailed implementation plan. Agents use task locks (work ownership records) through shared Git in separate containers (isolated work units); there is no central orchestrator. ([Carlini](https://www.anthropic.com/engineering/building-c-compiler))

GCC serves as the known-correct oracle: GCC compiles part of the kernel and the new compiler compiles the rest; failing combinations are reduced to find the cause. Test outputs are short and searchable; CI is tightened as widespread regressions (breakage of previous behavior) increase. Other agents consolidate duplicate code, improve compiler performance and generated code, and critique the Rust design. ([Carlini](https://www.anthropic.com/engineering/building-c-compiler))

**A 99% test pass rate does not mean the product is ready.** The article explicitly describes slower output code, a buggy assembler/linker (tools arranging/combining machine code), reliance on GCC for 16-bit x86 and quality below expert Rust code. The repo README says correctness has not been verified and advises against use; some README claims stronger than the blog's also cannot be treated as verified improvements. ([Carlini](https://www.anthropic.com/engineering/building-c-compiler); [dated README](https://raw.githubusercontent.com/anthropics/claudes-c-compiler/e6f3fad053d1ad5f3c9370dbc4221668d858ce6f/README.md))

### xAI/Grok's three different systems should not be conflated

The Grok foundation model, the `@grok` responder on X and the Grok Bot engineering product do not share the same evidence base. Lingxi Li's 10 September article shows five domain-specific bots directing Cursor cloud agents for Grok Bot. PR records are regularly scanned for CI, conflicts, Bugbot and security findings; low blast radius (the area a change can affect) and high confidence permit auto-merge, with Li reviewing code/evidence in other cases. Browser, CLI, accessibility paths and audio/transcript flows are tested on real development instances; failures lead to postmortems (incident cause reviews) and playbook updates. ([Grok Bot for Engineering](https://x.ai/bot/guides/grok-bot-for-engineering))

The planner in Grok Build's source code calls for three–five independently checkable criteria and observations verifying them; under uncertainty, the verifier must favor refutation (disproving the claim) and reject weakened criteria and fake tests. The browser rule says a single rendered screenshot is not verification. These are open-source prompt contracts, not evidence that they are met in every run. The sandbox being off by default and the Linux/macOS difference in network restrictions are also security limitations specific to this product. ([planner](https://raw.githubusercontent.com/xai-org/grok-build/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-shell/src/session/templates/goal_planner_prompt.md); [verifier](https://raw.githubusercontent.com/xai-org/grok-build/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-shell/src/session/templates/goal_verifier_prompt.md); [browser rule](https://raw.githubusercontent.com/xai-org/grok-build/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-agent/src/prompt/browser_verification.rs); [sandbox guide](https://raw.githubusercontent.com/xai-org/grok-build/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-pager/docs/user-guide/18-sandbox.md))

For the X responder's 2025 incidents, the company describes prompt-change review, monitoring and end-to-end red teaming (testing systems through adversarial scenarios); it attributes the July incident to an old higher-level code path independent of the foundation model. These incidents do not yield a complete lifecycle of how the Grok model or responder code was developed with agents. The company-wide share of agent-written code and these systems' spec/ticket/QA role contracts are **Not in sources**. ([full copy of the July explanation](https://twitter-thread.com/t/1943916977481036128); [prompt repo](https://raw.githubusercontent.com/xai-org/grok-prompts/a7c186f5ccac95875c0041aed60398f6ecb6d6c7/README.md); [Grok Bot-specific workflow](https://x.ai/bot/guides/grok-bot-for-engineering))

### Stripe places a code-defined workflow around the model

A Minion is an unattended agent that starts from Slack/ticket context and produces a PR. Stripe's goose fork uses a blueprint (a code-defined workflow): steps such as lint, Git and push are ordinary programs; implementation and CI-failure correction steps use agents. Each task runs in a prepared devbox (development machine); it cannot access real user data, production services or arbitrary network egress (outbound network access). Scoped rules (rules loaded only for the relevant file area) and a small, selected tool set keep context limited. ([Minions part 1](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents.md); [part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2.md))

CI selects relevant tests from a large test pool; autofix reduces remaining issues; the agent fixes and pushes once more. **Handing over to a human after at most two CI rounds does not mean CI is definitely green.** Every PR receives human review; a failed run can also be a starting point. More than 1,000/1,300 merges per week is the company's throughput (work completion rate) report; it cannot be converted into a quality rate because defect, revert and incident rates are not provided. ([part 1](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents.md); [part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2.md))

The later Payment Method Factory work connects a spec conversation and discrete steps to PRs; when the LLM coordinator sometimes writes code itself and exhausts its context, predictable coordination is moved into ordinary code. Requests, responses, state and events are checked in the provider sandbox, and fixed response contracts are recorded. The Extensibility SDK article describes a detailed spec reviewed by a human as a GitHub issue after prototyping, agent implementation and architectural-intent review; roughly twenty ESLint rules check sandbox/import/type boundaries. These fill in the spec and architecture examples missing from the two Minions articles. ([Payment Method Factory](https://stripe.dev/blog/stripes-payment-method-factory-orchestrating-agents-for-repeated-custom-integrations.md); [SDK](https://stripe.dev/blog/ai-didnt-write-our-sdk-it-changed-how-we-built-it.md))

### Expert review at Cloudflare catches some defects and misses others

Kenton Varda's OAuth library (a library for granting another application access) starts with a detailed API example; prompts and human corrections remain in commit messages. Review catches a serious cryptographic error allowing the key to be derived from the stored token ID; when Claude takes the wrong path on some fixes, the human corrects it manually. The human also later finds his earlier decision about refresh token rotation (changing the refresh token on every use) mistaken. This shows that the expert providing the spec can also be wrong. ([first commit](https://github.com/cloudflare/workers-oauth-provider/commit/3b2ae809); [crypto fix](https://github.com/cloudflare/workers-oauth-provider/commit/adcbb5de9c24f5b6a7dbea2e0a313a87c304d9bb); [failed fix](https://github.com/cloudflare/workers-oauth-provider/commit/bf729a54); [human intervention](https://github.com/cloudflare/workers-oauth-provider/commit/60197d5e); [decision change](https://github.com/cloudflare/workers-oauth-provider/commit/bf729a54b8c8556b0d55b2ae1c19baed3746909a))

Despite the claim of line-by-line expert review, two medium CVEs (registered security vulnerabilities) emerge: the authorize stage does not check that `redirect_uri` is allowlisted; PKCE (verification protecting against authorization code theft) can be bypassed through a downgrade. Fix PRs are merged on 30 April, and advisories are published on 1 May. Negative tests (tests of behavior that should be rejected) provide explicit checks of an attacker's redirect and the downgrade. Neil Madden criticizes inadequate tests; the view that review did not happen is his assessment, not an established fact. ([CVE-2025-4143](https://github.com/cloudflare/workers-oauth-provider/security/advisories/GHSA-4pc9-x2fx-p7vj); [CVE-2025-4144](https://github.com/cloudflare/workers-oauth-provider/security/advisories/GHSA-qgp8-v765-qxx9); [PR 26](https://github.com/cloudflare/workers-oauth-provider/pull/26); [PR 27](https://github.com/cloudflare/workers-oauth-provider/pull/27); [Madden](https://neilmadden.blog/?p=3982))

The October repo contract includes `npm run check`, tests for new behavior, CI, security invariants and human-only releases. A black-box conformance suite (checking compliance with a standard without using internal code) running against a real Worker has been added to run in CI; PKCE and redirect policy have moved to stronger defaults. This is a shift toward supporting stated confidence with more testable controls; it does not mean the checks were run here or that all security risks have been resolved. ([AGENTS](https://github.com/cloudflare/workers-oauth-provider/blob/main/AGENTS.md); [CI](https://raw.githubusercontent.com/cloudflare/workers-oauth-provider/602610ce1c11fdb412388713f66a4ca2a45c110d/.github/workflows/ci.yml); [conformance](https://raw.githubusercontent.com/cloudflare/workers-oauth-provider/602610ce1c11fdb412388713f66a4ca2a45c110d/conformance/README.md); [commit history](https://github.com/cloudflare/workers-oauth-provider/commits/main))

### Cursor's production setup differs from its browser experiment

For production code, Cursor describes Bugbot, repo-specific blocking security review, dependency reachability analysis (paths where a dependency is actually used), canary deployment (a limited initial release) and daily invariant checks. Cloud VMs use egress restrictions, narrow Git access, secret scanning and tool output redaction (hiding secrets in output). The `anydev` CLI starts and monitors services; Cloud Doctor investigates broken environments and misleading instructions. ([Bugbot](https://cursor.com/blog/building-bugbot); [security agents](https://cursor.com/blog/security-agents); [cloud environment](https://cursor.com/blog/cloud-agent-environment))

John Gilhuly's June talk describes a plan → human plan review → implementation/demo → release/retrospective workflow and automatic approval for low-impact work. His estimate of 30–40% of merges without human review is not a precise defect escape rate. Likewise, Bugbot's resolution rate (the proportion of its reported issues resolved) or Autofix's merge rate does not measure undiscovered bugs. ([Gilhuly, 04:48–05:09](https://www.youtube.com/watch?v=Lsp5YZ9Jj3Q&t=288s); [12:36–13:19](https://www.youtube.com/watch?v=Lsp5YZ9Jj3Q&t=756s); [Bugbot](https://cursor.com/blog/building-bugbot); [Autofix](https://cursor.com/blog/bugbot-autofix))

([Scaling agents](https://cursor.com/blog/scaling-agents); [Self-driving codebases](https://cursor.com/blog/self-driving-codebases); [Willison–Lin conversation, written source](https://simonwillison.net/2026/Jan/23/fastrender/); [HN discussion](https://news.ycombinator.com/item?id=46646777))

## OpenClaw's problem was an assurance gap, not an absence of tests

### Fast personal development was not the same process as a growing product

Peter Steinberger's 2025 account includes several strong Codex agents in the same folder, small commits directly to main, a plan evolving through conversation, screenshots and selective code review. He says he does not read most code; he has tests written after the feature in the same context; he also uses review bots, lint and refactoring (improving structure while preserving behavior). Describing all early code as unreviewed or all work as having no acceptance conditions would go beyond the sources. He explicitly says the method suits solo work. ([Just Talk To It](https://steipete.me/posts/just-talk-to-it/); [Shipping at Inference-Speed](https://steipete.me/posts/2025/shipping-at-inference-speed/))

The personal assistant started in November and moved from the names Clawdbot/Moltbot to OpenClaw in January; the first-party announcement is dated 29 January, while some news reports say 30 January. Steinberger says in February that he will join OpenAI, and the July foundation announcement says he continues making technical decisions. As of 14 October, there are roughly 392,000 stars and active releases; these are not quality measurements. ([Introducing OpenClaw](https://openclaw.ai/blog/introducing-openclaw); [joining OpenAI](https://steipete.me/posts/2026/openclaw/); [Foundation](https://openclaw.ai/blog/introducing-openclaw-foundation); [repo API](https://api.github.com/repos/openclaw/openclaw); [releases](https://github.com/openclaw/openclaw/releases))

**“There were no tests, CI or security considerations at the start” is false.** The 30 November sources include a TypeScript build, Biome lint, Vitest/coverage and CI. On 23 January, there are 887 `.test.` paths and lint/test/build/protocol checks; these are not a test case count or actual coverage measurement. January security documentation includes a threat model (a model describing attackers and the boundaries to protect), pairing, allowlists, networking and sandbox guidance. What was missing needs to be stated defect by defect. ([November package](https://raw.githubusercontent.com/openclaw/openclaw/c5677df56e1b90d2390acb91bc5784f4a657a687/package.json); [November CI](https://raw.githubusercontent.com/openclaw/openclaw/c5677df56e1b90d2390acb91bc5784f4a657a687/.github/workflows/ci.yml); [January tree](https://api.github.com/repos/openclaw/openclaw/git/trees/69f645c662c4888845f69f8b00477d7d42bde4f3?recursive=1); [January CI](https://raw.githubusercontent.com/openclaw/openclaw/69f645c662c4888845f69f8b00477d7d42bde4f3/.github/workflows/ci.yml); [security guide](https://raw.githubusercontent.com/openclaw/openclaw/69f645c662c4888845f69f8b00477d7d42bde4f3/docs/gateway/security.md))

### Later fixes do not erase past defects, but they change the assessment

In April, Steinberger describes permission, reconnect scope, sandbox, environment and approval defects, and accepting regressions during rapid hardening. In May, he says the project remained too dependent on its founder and he underestimated the transition. Two-person release gates, PR-level end-to-end CI, static scanners (tools scanning code without running it) and building a broader team are part of this account. Extended-stable (a more stable release supported until the next monthly line) arrives in July; this announcement does not say a formal long-term LTS has been completed. ([30 April](https://openclaw.ai/blog/openclaw-security-in-public); [5 May](https://openclaw.ai/blog/openclaw-rough-week); [extended-stable](https://openclaw.ai/blog/extended-stable-releases-and-maturity-scorecards))

Current rules call for independent expected values, production-path proof, owner review for restricted/security changes and CI at the current head. Skill scanning now uses multiple scanners and judges; October's limited benchmark results do not guarantee a flawless real-world filter. The security policy still rests on a single trusted operator, an execution sandbox disabled by default and plugins treated as trusted; this is the product's explicit trade-off (the cost of choosing between options). ([boundary-test guide](https://raw.githubusercontent.com/openclaw/openclaw/main/docs/help/testing/writing-tests.md); [maintainer workflow](https://raw.githubusercontent.com/openclaw/openclaw/main/.agents/skills/openclaw-pr-maintainer/SKILL.md); [ClawScan](https://openclaw.ai/blog/tencent-aig-joins-clawscan/); [security policy](https://raw.githubusercontent.com/openclaw/openclaw/4d2255b5f901d33ac5900555f949e44f0d614eb5/SECURITY.md))

The fair conclusion is that **actual execution checks against declared boundaries, regression evidence covering all sibling paths and update/recovery checks suited to real users were insufficient**. This is the notes' synthesis of confirmed defects; the conclusions “AI speed caused all defects”, “it would not happen if humans wrote it” or “there was no architecture” are Not in sources. Adding tests to VibeTunnel after breakages were felt is his own explicit statement; tracker counts do not justify an overall quality judgment for the other applications. ## A template repo should connect intent to a work contract and evidence

### Matt and Lauren complement each other; they are not two complete frameworks

Matt's 9 October snapshot has 27 plugin skills and 38 skills in total; some setup tools are in the frozen (no longer maintained) or beta sections. pstack's 14 October snapshot contains 53 registered skills, two agents and a separate Benny automation package; neither establishes an application/security/network framework for an entire project on its own. Lauren's private Dune is not a template delivered by installing pstack. ### PM, engineer, reviewer and QA do not mean the same thing by “done”

The failure example in Alexey Grigorev's article is a working CLI with 62 passing tests that is not the requested web retrospective product. First come the idea and `plan.md`, then stack options, MVP (minimum useful product) scope, a backlog (work list) and groomed issues (work made ready for implementation). The PM, the product manager, fills in Goal/Acceptance criteria/Out of scope/Constraints before coding; the human reviews this issue. ([Alexey](https://aishippingblog.com/p/ai-native-development-specifications))

The engineer implements without changing the criteria, runs behavior tests and the entire test suite, and leaves a commit and implementation comment; they do not close the issue. QA, the quality verifier, **independently tests every criterion in the running code**, looks for missing test cases and records actions and observed results; one failed criterion means FAIL, and QA does not change code. The orchestrator (the role directing the workflow) closes the issue only after QA PASS. Alexey says this role graph costs time/tokens and is not needed for every task; the text does not claim integration with Matt or pstack. ([Alexey](https://aishippingblog.com/p/ai-native-development-specifications))

### A spec's correctness should be checked with three separate questions

The first question is **“Did we write what the user wanted?”** Matt's spec guide describes a good result as one where the user remembers making every decision and the document invents nothing to fill a section. Alexey's wrong-CLI example shows that tests do not answer this question. Superpowers' builder check then looks for whether another implementer would have to make an important guess. ([Matt spec guide](https://www.aihero.dev/skills-to-spec); [Alexey](https://aishippingblog.com/p/ai-native-development-specifications); [builder check](https://github.com/obra/superpowers/blob/main/skills/brainstorming/builder-check-prompt.md))

The second question is **“Is the text internally feasible and consistent?”** Requirements need explicit triggers and expected outcomes, independent user journeys, measurable success, scope and actual constraints. Kiro cross-requirement analysis raises contradictions as questions; Spec Kit `analyze` looks for duplicates, ambiguities and unmapped requirements (requirements not connected to work) across spec/plan/tasks; Superpowers pre-flight examines tasks sharing the same file/interface and each task's internal consistency. These AI analyses are aids; a plan linter's format checks do not replace them either. ([Kiro](https://kiro.dev/docs/specs/analyze-requirements/); [Spec Kit spec](https://github.com/github/spec-kit/blob/96774bc52fd7dccc7185791e1cac7572b9e09dea/templates/spec-template.md); [analyze](https://github.com/github/spec-kit/blob/96774bc52fd7dccc7185791e1cac7572b9e09dea/templates/commands/analyze.md); [Superpowers pre-flight](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/executing-plans/SKILL.md); [pstack linter](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/skills/poteto-mode/scripts/check-plan.mjs))

The third question is **“Does the product actually do this?”** A pre-approved scenario, a snapshot of old behavior or an independent external contract provides a more independent acceptance source than an expected value calculated from the new implementation itself. Ronacher's old Rust snapshots, Carlini's GCC, Stripe's recorded provider responses and Alexey's running-code checks are different examples of this. A checkmark in Spec Kit's requirements checklist shows that requirement quality was reviewed; it does not show that the code performs that behavior. ([MiniJinja](https://lucumr.pocoo.org/2026/1/14/minijinja-go-port/); [compiler](https://www.anthropic.com/engineering/building-c-compiler); [Stripe Factory](https://stripe.dev/blog/stripes-payment-method-factory-orchestrating-agents-for-repeated-custom-integrations.md); [Alexey](https://aishippingblog.com/p/ai-native-development-specifications); [Spec Kit checklist](https://github.com/github/spec-kit/blob/96774bc52fd7dccc7185791e1cac7572b9e09dea/templates/commands/checklist.md))

Lauren gives no hard line cap for PRs; Matt wants work to fit a fresh context window; a safe context limit for a small model is **Not in sources**. ### “Done” should be a falsifiable result, not a feeling or checkbox

pstack's example initial prompt expresses this concisely: **“done means the 60k-row fixture exports every row. show me the row counts before and after.”** Another actual done example is “done means zero old callers, all parser fixtures pass, old api deleted.” Both provide an observable endpoint instead of “improve it” or “work for four hours”. ([prompt guide](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/docs/guide/02-poteto-mode.md); [autonomous work guide](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/docs/guide/07-overnight.md))

| Task given in the source | Done given in the source | Gap to fill before the ticket can be considered ready |
|---|---|---|
| Export 60,000 rows | All rows exported; evidence of before/after row counts | The actual fixture path, export command and error/permission scenarios for this example are Not in sources. We cannot copy the example and treat it as a complete executable ticket. ([prompt guide](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/docs/guide/02-poteto-mode.md)) |
| Replace an old API | Zero old callers, all parser fixtures pass, old API removed | The specific repo's API name, search and test commands are Not in sources; they must come from that repo. ([overnight work contract](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/docs/guide/07-overnight.md)) |
| Benny bug fix | The same real UI path shows the broken state before and expected state after, following two resets; cross-checking media and stored state; tests and nearby flows; draft PR | An unreproducible or blocked path does not count as passed; this workflow does not merge. ([reproduce-and-fix](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/automations/benny/skills/reproduce-and-fix-issues/SKILL.md)) |
| Alexey's issue | QA tested every criterion in running code; one failure means FAIL; close only after PASS | A general browser/CLI adapter in the article is Not in sources; the verification environment depends on the project. ([article](https://aishippingblog.com/p/ai-native-development-specifications)) |

A ticket's completion record needs to be distinguished from issue/release completion. The implementer may say “code and tests are ready”; the reviewer may assess spec/quality from the diff; QA records the actual criterion as PASS/FAIL/INCONCLUSIVE (successful/failed/inconclusive). If a criterion could not be run, evidence for “done” is incomplete; pstack does not count wrong-surface or inconclusive results as passes, and Alexey ties issue closure to the QA result. If code changes, which changes an old verdict still applies to is checked separately; pstack tracks this through SHA and patch-id (an identifier of change content). ([feature playbook](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/skills/poteto-mode/playbooks/feature.md); [figure-it-out](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/skills/figure-it-out/SKILL.md); [Alexey](https://aishippingblog.com/p/ai-native-development-specifications); [shipping](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/skills/poteto-mode/playbooks/shipping.md); [14 October plan](https://github.com/cursor/plugins/blob/ce649c03ac3b75b6ae80cbd15b7e2c536caedb5a/pstack/skills/poteto-mode/playbooks/multi-phase-plan.md))

The reviewer must see the brief, check the implementation against the criteria and state what it cannot know. QA must exercise the user path, persistence and relevant side effects rather than merely reading the report. When the spec, tests and implementation derive from the same wrong assumption, all three can be consistent with each other; independent oracles/fixtures and human intent checks are therefore separate supports. This conclusion is a synthesis of the notes, not a guarantee of zero reviewer misses. ([Superpowers reviewer](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/subagent-driven-development/task-reviewer-prompt.md); [Alexey QA](https://aishippingblog.com/p/ai-native-development-specifications); [Atlas](https://github.com/poteto/verification-skill-example/blob/d5abe70d0d8c671672b6cef4069363f26c488feb/.cursor/skills/verify-atlas/SKILL.md); [Ronacher oracle](https://lucumr.pocoo.org/2026/1/14/minijinja-go-port/); [Böckeler test critique](https://martinfowler.com/articles/exploring-gen-ai/tdd-in-the-agent-loop.html))

## Conclusion

A template repo's claim should not be an unlimited “the agent cannot make mistakes”; it should be **which mechanism rejects which error, and which actual defect it was tested against**. This goal is grounded in the sources through Lauren's requirement to turn past errors into checks, Matt's clarity of behavior/decisions and the independent QA contract. Such a repo's quality offering is more than starter code; it is an evidence path connecting a new change to its intent, boundaries and running result. This is the notes' shared inference, not a verified universal solution. ([Lauren correct](https://github.com/cursor/plugins/blob/c86f349b102feb91f1966f8a6a60882a4e601b50/pstack/skills/correct/SKILL.md); [Matt agent brief](https://github.com/mattpocock/skills/blob/49dd158/skills/engineering/triage/AGENT-BRIEF.md); [Alexey](https://aishippingblog.com/p/ai-native-development-specifications); [Atlas proof](https://github.com/poteto/verification-skill-example/blob/d5abe70d0d8c671672b6cef4069363f26c488feb/.cursor/skills/verify-atlas/SKILL.md))

For the next assessment, a more valuable question than “how many agents or PRs were produced?” is **when the small implementer made a mistake, which gate actually stopped it, what could the reviewer not assess, and which criterion was tested live?** A reviewer without a brief, 62 tests checking the wrong product and a tool path bypassing sandbox policy show why quality labels are insufficient. The sources provide material for asking these questions and setting up existing mechanisms; they do not provide proof of reaching zero defects in every project. ([Vincent evaluation](https://blog.fsck.com/2026/06/15/Superpowers-6/); [Alexey](https://aishippingblog.com/p/ai-native-development-specifications); [Snyk](https://labs.snyk.io/resources/bypass-openclaw-security-sandbox/))

Lauren's June article adds two more conditions to this assessment: a stage must be able to stop progress, and the situations covered by the evidence must be explicit. The StyleX example shows real use finding bugs even when recorded images are correct. The figure of 2,500 PRs does not close this gap. It is therefore reasonable to recommend that a starter repository learn from a small number of real tasks and improve its evidence path before expanding scope. This is a recommendation drawn from the sources, not a general guarantee of success. ([Loops You Can Trust](https://x.com/poteto/status/2069824386283319343); [2,500 PR post](https://x.com/poteto/status/2102050467505430555))

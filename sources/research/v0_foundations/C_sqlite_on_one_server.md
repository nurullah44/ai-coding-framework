# C: SQLite on one Hetzner server

## 1. Decision for this product

**Synthesis: SQLite is a defensible choice here, provided the workload tolerates serialized writes and the database stays on suitable local storage. Daily Hetzner server backups alone do not establish a reliable database recovery plan.** SQLite's authors explicitly allow website/application-server use; Hetzner explicitly declines to guarantee consistency of images made from a running server. [SQLite fit](https://www.sqlite.org/whentouse.html), [Hetzner consistency FAQ](https://docs.hetzner.com/cloud/servers/backups-snapshots/faq/)

The supplied Cloudflare/Tailscale setup describes network exposure, not the write workload or storage guarantees. **Synthesis:** it does not answer the SQLite concurrency or backup questions. No source reviewed gives AI-written applications a different database capacity threshold. The relevant documented properties are locking, transaction behavior and recoverable backups. [SQLite isolation](https://www.sqlite.org/isolation.html), [backup API](https://www.sqlite.org/backup.html)

## 2. Fit and concurrency

SQLite's authors say it fits most low to medium traffic websites. Their checklist explicitly allows an application server with the database on the same machine, even when users connect over the network. They favor a client/server engine for write-intensive sites, sites needing multiple servers, direct database access from many networked computers, or writers that cannot queue and take turns. This develops the earlier notes' fit discussion without converting HTTP hits into users. [Appropriate uses, sections 1 to 3](https://www.sqlite.org/whentouse.html)

- **Several processes are supported.** Separate connections can belong to separate processes; SQLite coordinates their writes with locks. Web processes, workers and administrative connections can share one database on one host, but must take turns writing. Adding processes does not add simultaneous writers to one file. [Isolation between connections](https://www.sqlite.org/isolation.html)
- **WAL improves read/write overlap.** Enable with `PRAGMA journal_mode=WAL;` and check that it returns `wal`. Readers can proceed while a writer appends changes. There is still only one writer per database. WAL requires all processes on one host and does not work over a network filesystem. [WAL overview and concurrency](https://www.sqlite.org/wal.html)
- **A busy timeout is waiting, not extra capacity.** Configure it for every connection, including connections from pools and workers. `sqlite3_busy_timeout()` retries lock acquisition by sleeping, then returns `SQLITE_BUSY` after its waiting budget; zero disables the handler. A five-second timeout is Litestream's recommendation, not a SQLite throughput promise. [SQLite timeout API](https://www.sqlite.org/c3ref/busy_timeout.html), [Litestream busy timeout](https://litestream.io/tips/#busy-timeout)
- **Timeouts do not eliminate transaction retries.** SQLite can return `SQLITE_BUSY` without invoking the busy handler to avoid deadlock. A stale WAL read transaction upgraded to a writer can fail with `SQLITE_BUSY_SNAPSHOT`; SQLite documents ending that transaction and starting a new one. `BEGIN IMMEDIATE` acquires the write transaction earlier, occupying the writer slot earlier too. [Busy handler](https://www.sqlite.org/c3ref/busy_handler.html), [isolation examples](https://www.sqlite.org/isolation.html)
- **Watch transaction duration and checkpoints.** Long readers can prevent checkpoint completion and allow WAL growth. **Synthesis:** keep transactions short and measure busy errors, write latency and WAL size against this product's acceptance criteria. An exact safe number of workers or writes per second is **Not in sources**. [WAL checkpointing](https://www.sqlite.org/wal.html#checkpointing)

**Version caveat:** the authors report a rare WAL write/checkpoint race fixed in SQLite 3.51.3, with backports in 3.44.6 and 3.50.7. **Synthesis:** check the SQLite library actually linked into the application image for that fix, including a vendor backport. [WAL-reset bug and fixed versions](https://www.sqlite.org/wal.html#walresetbug), [3.51.3 release notes](https://www.sqlite.org/releaselog/3_51_3.html)

## 3. Docker and the actual filesystem

Docker documents volumes as persistent storage outside a container's writable layer, and supports mounting one volume into multiple containers. Volumes can also use NFS, CIFS or other drivers. Even the `local` driver can mount NFS, so its name alone does not establish that the data is on a local disk. [Docker volumes](https://docs.docker.com/engine/storage/volumes/)

SQLite relies on filesystem locks to coordinate processes. Its corruption guide warns that missing or broken locking, particularly on NFS, can corrupt a database under concurrent access. All connections must use compatible locking protocols. [How To Corrupt, section 2](https://www.sqlite.org/howtocorrupt.html#_file_locking_problems)

SQLite's general discussion allows some remote-file use with qualifications; this is not a promise that WAL works over NFS. Its network-storage guidance discusses rollback mode or keeping WAL access behind a process on the database host, and warns that network-filesystem locking and synchronization vary by implementation. [SQLite over a network](https://www.sqlite.org/useovernet.html)

**Synthesis for this deployment:** mount a persistent directory containing the database and its sibling files from the host's local filesystem into every process/container that uses it. Give them access to the same files and the required directory permissions. This combines Docker's volume model with SQLite's same-host WAL and shared-file requirements; it is not an explicit SQLite certification of every Docker/storage-driver/filesystem combination. A blanket Docker compatibility guarantee is **Not in sources**. [Docker volume mounts](https://docs.docker.com/engine/storage/volumes/), [WAL files and permissions](https://www.sqlite.org/wal.html#read_only_databases)

**Docker volume versus Hetzner Volume:** a Docker volume whose host directory is on the Cloud server's included disk belongs to that disk's contents (inference). A Docker volume or bind mount backed by an attached **Hetzner Cloud Volume** is excluded from Cloud Backups/Snapshots. Inspect the host mount backing the database, not just its container path. This coverage distinction does not establish database consistency. [Docker storage](https://docs.docker.com/engine/storage/volumes/), [Hetzner backup coverage](https://docs.hetzner.com/cloud/servers/backups-snapshots/overview/)

## 4. Database backups and live server images

### Copying a live database

**An ordinary `cp`, `tar` or file-by-file `rsync` of a changing database is not a safe SQLite backup procedure.** SQLite warns that copying during a transaction can mix old and new content and produce corruption. It permits copying when no transactions occur throughout the copy, keeping any required journal together with the database. [How To Corrupt, section 1.2](https://www.sqlite.org/howtocorrupt.html#_backup_or_restore_while_a_transaction_is_active)

In WAL mode, committed data can still be in `app.db-wal`. It is part of persistent database state. Copying `app.db` alone can lose commits or corrupt the copy; sequentially copying the WAL afterwards does not establish a common point in time (inference). The `-shm` file coordinates readers and writers but contains no database content and is not required for crash recovery. Do not delete live sidecar files to simplify backups. [WAL persistent state](https://www.sqlite.org/wal.html#the_wal_file), [WAL file format](https://www.sqlite.org/walformat.html#the_wal_index_or_shm_file)

### SQLite-aware ways to create a separate backup

| Method | Documented behavior and limits | Source |
|---|---|---|
| Online Backup API | Makes a consistent destination database. Can copy incrementally, locking the source only during individual read steps. Other connections' writes can restart it. Check `sqlite3_backup_step()` reaches `SQLITE_DONE`; `sqlite3_backup_finish()` returning `SQLITE_OK` alone does not prove completion. | [Backup overview](https://www.sqlite.org/backup.html), [API completion/errors](https://www.sqlite.org/c3ref/backup_finish.html) |
| `sqlite3` shell `.backup` | The shell documents `.backup ?DB? FILE` to back up the selected database, defaulting to `main`. Litestream's scheduling guide explicitly recommends it as a safe live backup command. | [CLI commands](https://www.sqlite.org/cli.html#special_commands_dot_commands_), [scheduled backup guide](https://litestream.io/alternatives/cron/) |
| `VACUUM INTO` | Produces a compact, consistent snapshot without changing the source. Uses more CPU than the backup API and cannot be incremental. Target must be absent or empty. Interruption can leave an incomplete/corrupt output. Current docs say a completed output is synced when the source connection uses `synchronous=NORMAL` or `FULL`, assuming correct OS/filesystem/hardware. | [VACUUM INTO](https://www.sqlite.org/lang_vacuum.html#vacuum_with_an_into_clause) |
| `sqlite3_rsync` | SQLite's own database-aware remote-copy utility, distinct from ordinary `rsync`. Copies live databases over SSH. It can be scheduled; it is not continuous replication. | [SQLite remote-copy tool](https://www.sqlite.org/rsync.html) |

Example command forms, adapted from the documented CLI/SQL syntax. They illustrate separate alternatives, not a production scheduling or retention script. [CLI](https://www.sqlite.org/cli.html), [VACUUM INTO](https://www.sqlite.org/lang_vacuum.html#vacuum_with_an_into_clause)

```sh
sqlite3 /data/app.db ".backup '/backups/app-2026-10-16.sqlite'"
sqlite3 /data/app.db "VACUUM INTO '/backups/app-2026-10-16-vacuum.sqlite';"
```

**Suggested procedure, synthesis:** create a uniquely named SQLite-native backup, require success, copy the completed artifact off the server, retain historical copies and rehearse restoring one into a separate environment. The native API addresses consistency; the off-server copy addresses losing the host. A backup job that only creates another file on the same disk does not provide that separation. [SQLite backup API](https://www.sqlite.org/backup.html), [Hetzner storage/backup guidance](https://docs.hetzner.com/storage/general/which-storage-is-right-for-me/)

For a recovery rehearsal, SQLite documents `PRAGMA integrity_check;` and `PRAGMA foreign_key_check;`. The first does not check foreign-key violations. **Synthesis:** also start the app against the restored copy and verify known records and critical operations, since structural integrity alone does not prove that the expected business data was backed up. [Integrity and foreign-key checks](https://www.sqlite.org/pragma.html#pragma_integrity_check), [Litestream restore/testing guide](https://litestream.io/alternatives/cron/#restoring--testing-backups)

### Is a running-server disk snapshot consistent?

**Hetzner recommends powering off the server for disk consistency and does not guarantee consistency for images of running systems.** A guaranteed consistent live SQLite backup is **Not in sources**. [Hetzner FAQ](https://docs.hetzner.com/cloud/servers/backups-snapshots/faq/)

**Conditional technical inference:** a coherent, atomic image of the database and matching WAL, with correct persistence/write ordering, could be recovered as a crash state. SQLite rebuilds its WAL index from valid committed WAL frames. This differs from gradually copying changing files. [SQLite WAL recovery](https://www.sqlite.org/walformat.html#recovery)

A Hetzner promise of atomic capture, guest-cache flushing or SQLite coordination is **Not in sources**. This leaves live-image recoverability unguaranteed, rather than proving every such image corrupt. [Hetzner's stated limit](https://docs.hetzner.com/cloud/servers/backups-snapshots/faq/)

Consistency also differs from durability: in WAL mode, `synchronous=NORMAL` preserves consistency but some committed transactions can roll back after power loss/system crash. `FULL` adds a WAL sync at each commit for durability. Neither setting supplies an off-server backup or strengthens Hetzner's image guarantee (synthesis). [SQLite synchronous settings](https://www.sqlite.org/pragma.html#pragma_synchronous)

### What the Hetzner Cloud service actually provides

- **Frequency/retention:** automatic daily Backups, seven slots per server, with the oldest replaced when full. Snapshots are manually created and persist until deletion. These are disk images, not per-transaction database history. [Backup/Snapshot overview](https://docs.hetzner.com/cloud/servers/backups-snapshots/overview/)
- **Scheduling/lifecycle:** Hetzner selects the automatic backup timeframe; customers cannot select that time. Deleting a server also deletes its Backups. Snapshots survive deleting their source server, and a Backup can be converted to a Snapshot. [Backup FAQ](https://docs.hetzner.com/cloud/servers/backups-snapshots/faq/)
- **Restore:** rebuild an existing server from the image, overwriting its disk, or create a new server from the Backup/Snapshot. For a rehearsal, use a new server (recommendation). [Restore/duplicate behavior](https://docs.hetzner.com/cloud/servers/backups-snapshots/overview/)
- **Coverage:** attached Hetzner Volumes are excluded and do not have this Backup/Snapshot feature. They are networked block storage, not NFS/SMB file shares; do not conflate the storage layers. This does not change their backup exclusion. [Hetzner Volumes](https://docs.hetzner.com/cloud/volumes/overview/)

**Daily backup data-loss window, calculation:** with valid captures every 24 hours, failure just before the next capture can lose almost 24 hours of changes. Measure age from the latest **successfully restorable data point**. Failed copies or excluded storage can mean older data or no recovery point. A strict maximum interval between usable copies is **Not in sources**. Seven slots provide history, not a shorter loss window. [Hetzner daily frequency/coverage](https://docs.hetzner.com/cloud/servers/backups-snapshots/overview/)

**Same calculation for native backups:** a successfully exported and remotely copied database every hour targets roughly an hour of data loss, with extra age from backup/upload delay or failures. Daily native exports still target roughly a day. Native backup improves consistency, and off-server transfer improves survival; neither by itself changes a daily schedule into continuous protection. These are deductions from the scheduled-copy model. [Litestream scheduled backup guide](https://litestream.io/alternatives/cron/)

### If this is a dedicated root server

Do not transfer Cloud Backups' schedule, slots or restore UI assumptions to a dedicated root server. Hetzner says dedicated root-server customers are responsible for backing up their data; its dedicated-server FAQ offers Storage Boxes as backup space. The actual backup software, schedule, retention and bare-metal restore procedure must therefore be identified for this server. A dedicated-root-server equivalent of the Cloud feature is **Not in sources** reviewed here. [Root-server responsibility](https://docs.hetzner.com/robot/general/server-auction-faqs/), [dedicated-server backup space](https://docs.hetzner.com/robot/dedicated-server/faq/faq/)

A Storage Box provides a destination; a snapshot of a Storage Box captures that box, not the attached server's disk. **Synthesis:** export SQLite consistently, transfer the finished file to the destination, and document restoring both host/app and database. If someone says daily backups are enabled on a dedicated server, check that job's actual behavior rather than assuming Cloud semantics. [Hetzner storage comparison](https://docs.hetzner.com/storage/general/which-storage-is-right-for-me/), [backup responsibility](https://docs.hetzner.com/general/company-and-policy/data-protection-at-hetzner/)

## 5. Continuous protection and related tools

**Litestream:** runs beside the app and continuously copies SQLite WAL changes to a replica destination. The retrieved v0.5 documentation describes LTX transaction-log files and snapshots; restore reconstructs a database from retained remote history. Docker deployment can use a separate Litestream container sharing the app's local data volume. This is database replication for recovery; app binaries, uploaded files and server configuration need their own coverage (synthesis). [How it works](https://litestream.io/how-it-works/), [Docker guide](https://litestream.io/guides/docker/)

Its documented boundaries matter:

- It requires WAL and may take short write locks for checkpoints. It recommends the app configure a busy timeout. It does not add simultaneous SQLite writers. [Litestream caveats](https://litestream.io/tips/), [SQLite isolation](https://www.sqlite.org/isolation.html)
- Replication is **asynchronous**. The documented default sends changes to S3 every second; a catastrophic failure can lose changes not yet replicated. This is not a guaranteed one-second maximum loss window: upload delay, outages or a stopped replicator can make the remote copy older (inference). Synchronous replication is listed as unimplemented in the caveats. [Data-loss window](https://litestream.io/tips/#data-loss-window)
- Multiple applications replicating into the same bucket/path can make restoration impossible. Database deletion/recreation needs the documented metadata reset procedure. [Destination and lifecycle caveats](https://litestream.io/tips/)
- Retention must be configured deliberately. The current configuration docs default full snapshots and their retention to `24h`, and `l0-retention` to `5m`. They are not a promise of arbitrarily old recovery points. Restore replays whole retained LTX files; compaction/retention can make fine-grained historical points unavailable. [Configuration defaults](https://litestream.io/reference/config/#configuration-defaults), [restore granularity](https://litestream.io/how-it-works/#restore-granularity)

**Operational synthesis:** monitor successful remote replication, backup age and restore success. Rehearse restoring from the remote destination onto a replacement host, rather than testing only a local file. Define acceptable loss and recovery time first; shorter snapshot intervals can reduce restore work. The retrieved docs also describe VFS read replicas, so the blanket claim that Litestream has no read-replica capability would be outdated. That capability does not make the basic backup sidecar an automatic application failover system. [Snapshots/restore](https://litestream.io/how-it-works/), [disaster-recovery purpose and alternatives](https://litestream.io/alternatives/)

**Related approaches, with different purposes:**

- **Scheduled native backups:** Litestream's authors explicitly recommend hourly/daily SQLite backups when continuous protection is unnecessary, and as a possible fallback alongside Litestream. This is the simpler recovery option when its loss window is acceptable. [Alternatives](https://litestream.io/alternatives/)
- **LiteFS:** replicates SQLite across machines using a distributed filesystem. Writes go to a primary, and replication has no fixed completion-time guarantee. Current Fly docs say they cannot provide support/guidance, identify the project as pre-1.0 and still recommend off-site backups. Its extra topology is relevant when multiple nodes become a requirement (synthesis), not necessary merely to back up this one server. [LiteFS status](https://docs.fly.io/litefs), [primary routing](https://fly.io/docs/litefs/primary/), [replication position](https://fly.io/docs/litefs/position/)
- **rqlite:** a separate Raft-based database service built on SQLite, not a sidecar that continuously copies an existing app's SQLite file. Writes go through its leader/API and require quorum in the normal path. Its FAQ says it does not scale writes and a single node provides no redundancy. **Synthesis:** adopting it changes application access and deployment, and adds little fault tolerance while everything remains on one host. [rqlite FAQ](https://rqlite.io/docs/faq/)

## 6. Moving to PostgreSQL later

**Real migration work, not a guaranteed configuration swap.** SQLite's authors explicitly warn that applications relying on its flexible typing can fail when moved to PostgreSQL. The chosen framework/ORM, schema and queries are unspecified, so this product's migration time or downtime is **Not in sources**. [SQLite porting caveats](https://www.sqlite.org/quirks.html#flexible_typing)

Areas to inspect and migrate:

1. **Types and existing values:** ordinary SQLite tables can store text in integer columns and do not enforce declared `VARCHAR(n)` lengths. Booleans use integer representations; dates can be text/numbers. PostgreSQL has distinct boolean, timestamp, numeric, binary and other types. Decide conversions and validate actual stored data, rather than translating type names alone (recommendation). [SQLite type differences](https://www.sqlite.org/quirks.html), [PostgreSQL types](https://www.postgresql.org/docs/current/datatype.html)
2. **SQL behavior:** SQLite accepts aggregate queries with bare columns that PostgreSQL rejects unless grouping/functional-dependency rules are satisfied. Audit raw queries, functions and SQLite-specific pragmas. Example: `SELECT max(salary), first_name FROM employee` relies on SQLite behavior and needs rewriting for PostgreSQL. [SQLite aggregate behavior](https://www.sqlite.org/quirks.html#aggregate_queries_can_contain_non_aggregate_result_columns_that_are_not_in_the_group_by_clause), [PostgreSQL grouping](https://www.postgresql.org/docs/current/sql-select.html#SQL-GROUPBY), [SQLite-specific pragmas](https://www.sqlite.org/pragma.html)
3. **Keys and generated IDs:** SQLite's `INTEGER PRIMARY KEY` aliases its rowid; PostgreSQL identity columns use sequences. Preserve IDs and relationships during import, then set the PostgreSQL sequence state appropriately before new inserts (migration recommendation). [SQLite generated IDs](https://www.sqlite.org/autoinc.html), [PostgreSQL identity](https://www.postgresql.org/docs/current/ddl-identity-columns.html), [sequence functions](https://www.postgresql.org/docs/current/functions-sequence.html)
4. **Schema migration history:** migration SQL can depend on the engine. SQLite documents rebuilding a table for some schema changes; PostgreSQL has its own `ALTER TABLE` operations. As a concrete ORM example, Prisma Migrate v6 says provider-specific migration files cannot automatically switch SQLite/PostgreSQL; creating a fresh history also does not transfer data. This illustrates the problem, not an assumption that this app uses Prisma. [SQLite schema changes](https://www.sqlite.org/lang_altertable.html#making_other_kinds_of_table_schema_changes), [PostgreSQL ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html), [Prisma v6 limitation](https://www.prisma.io/docs/orm/v6/prisma-migrate/understanding-prisma-migrate/limitations-and-known-issues)
5. **Data transfer and cutover:** create the target schema, transform/load data, verify counts/relationships and app behavior, and plan how writes stop or are reconciled during the final transfer. This is a recommended migration procedure, not a one-command recipe from the sources. PostgreSQL `COPY` supplies import/export, but does not translate a SQLite schema or application semantics. [PostgreSQL COPY](https://www.postgresql.org/docs/current/sql-copy.html), [SQLite porting warning](https://www.sqlite.org/quirks.html)

**Reduce avoidable future work, synthesis:** use explicit constraints, enable/check foreign keys on each SQLite connection, consider `STRICT` tables, and isolate engine-specific SQL. SQLite `STRICT` accepts a small type set, so it does not make the schema PostgreSQL-compatible. Test against PostgreSQL when compatibility becomes an actual requirement; do not assume an ORM erases the differences. [Foreign-key configuration](https://www.sqlite.org/foreignkeys.html#fk_enable), [STRICT tables](https://www.sqlite.org/stricttables.html), [Prisma example](https://www.prisma.io/docs/orm/v6/prisma-migrate/understanding-prisma-migrate/limitations-and-known-issues)

## 7. PostgreSQL on this same server

PostgreSQL adds a database server process and a client/server connection model. Its MVCC and row-level locking support a different concurrency model from SQLite's single writer, although conflicting row updates still wait. Docker packaging does not make it a managed database. **Synthesis:** this fits when write contention, PostgreSQL features or a planned separate database host justify the extra service. It does not remove the common failure of the one machine hosting both app and database. [PostgreSQL architecture](https://www.postgresql.org/docs/current/tutorial-arch.html), [MVCC](https://www.postgresql.org/docs/current/mvcc-intro.html), [row locks](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS), [official Docker image](https://github.com/docker-library/docs/blob/master/postgres/README.md)

It still needs database-aware recovery: `pg_dump` creates a consistent logical backup while normal work continues. For continuous recovery, PostgreSQL documents base backups plus a continuous WAL archive. Its filesystem-backup docs permit coherent frozen snapshots with required WAL, but ordinary live file copies need shutdown. **Synthesis:** Hetzner's live-image consistency disclaimer therefore remains relevant after an engine switch. [pg_dump](https://www.postgresql.org/docs/current/backup-dump.html), [continuous archiving](https://www.postgresql.org/docs/current/continuous-archiving.html), [filesystem backup rules](https://www.postgresql.org/docs/current/backup-file.html)

## 8. Choice for this product

**Recommendation, synthesis:** keep server images as one recovery layer. For SQLite, start with scheduled native backups copied off the server if the owner accepts their loss window. Add Litestream when fresher recovery justifies operating it. Database choice and backup frequency remain separate decisions. [SQLite native backups](https://www.sqlite.org/backup.html), [periodic versus continuous](https://litestream.io/alternatives/)
